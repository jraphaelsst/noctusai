# Social Wiring

The real-estate operations hub of noc: lead intake, the sales funnel and cards,
properties and owners, contracts and certificates, marketing, and the WhatsApp
transport for **Julia**, the SDR agent. One seed-factory, single-container
product (backend 8011, frontend 8160, Supabase schema `social_wiring`).

Social Wiring is the **transport + CRM + operations** side. The agent's brain
(prompt, tools loop, LLM keys) is hosted in the `agents` product (Agent Studio)
and consumed over `/api/channels/*`; SW never calls an LLM for Julia's turns.

## Stack

- **Backend**: FastAPI via `create_product_app()` from `noctusai_seed`; features are product modules assembled from the `MODULES` list in `app/main.py` (`app/modules/*`) plus the Julia routers in `app/routers/julia_*`.
- **Frontend**: React via `createProductApp()` + `createProductLayout()` from `@noctusai/seed`; nav in `src/nav/navGroups.ts` (seed module groups CRM/Redes Sociais/ERP/CMS/... in canonical order; Julia pages in `src/nav/julia.ts`).
- **Database**: Supabase, schema `social_wiring`; RLS own-org + service role.
- **Auth**: SSO + direct login (seed factory); `/chat` and the Julia privacy notice (`/privacidade/:slug`) are public.
- **Container**: ONE container — uvicorn serves the built SPA + API on one port (`serve_spa`).

## The Julia module

Julia is the WhatsApp SDR for a real-estate org (renamed from "Lais" on
2026-10-19; Lais is Lastro's product, studied in a private study outside git).

- **Julia is hosted in agents** (julia-v2): her prompt, knowledge, qualification standard, controls (ligado/drenando/desligado, per-conversation pause) and the shared lead thread all live there; SW is transport + CRM + operations and consumes her **through the API only** (`app/clients/agents.py`). SW never gates on a cached copy of a control: agents decides on every turn and answers with a `status`; any non-served status, error or timeout sends nothing (fail closed).

### Enabling the WAHA webhook HMAC (NOC-REMEDIATE[waha-hmac-prod], runbook)

**Status: DONE in prod 2026-11-04 15:05Z** (`WAHA_WEBHOOK_HMAC_SECRET` is set; WAHA signs and SW enforces, so the webhook freshness/replay checks are live). The steps below stay as the runbook for another environment or a rotation. Without the secret SW accepts unsigned webhooks
**loudly**: one ERROR `webhook_hmac_desativado` per process and `GET /api/health` -> `startup_hook_error: "WebhookHmacDesativado: webhook_hmac_desativado"`
(`app/webhook_hmac.py`). With the secret set, an unsigned or badly signed webhook is a strict 401. To enable (owner-approved step, after deploy):
1. Generate the secret: `openssl rand -hex 32`.
2. Put it in the VPS root `.env` as `WAHA_WEBHOOK_HMAC_SECRET=<secret>` (read by social-wiring through `env_file`; not a compose-interpolated name, so it is NOT in `deploy/fleet/env.fleet.keys`, whose manifest is blocking-only).
3. Set the SAME value as `hmac.key` on the shared WAHA session's webhook config (`config.webhooks[].hmac.key`, WAHA signs with `X-Webhook-Hmac` + `X-Webhook-Hmac-Algorithm`, sha512 by default; SW verifies it with the seed `waha` scheme. Set WAHA's signing FIRST, then SW's secret — while SW's secret is unset it accepts unsigned calls, so there is no gap), and restart that session.
4. Recreate social-wiring (`noctus.dev.deploy_image` or `noctus.vps.recreate`).
5. Verify one signed inbound: send a WhatsApp message to the Julia line, confirm it arrives in Conversas, that `/api/health` has `startup_hook_error: null`, and that an unsigned `curl -X POST .../api/whatsapp/webhook/<token>` returns 401.
Rollback: unset the key in the root `.env` and recreate (SW falls back to the loud accept-unsigned state).
