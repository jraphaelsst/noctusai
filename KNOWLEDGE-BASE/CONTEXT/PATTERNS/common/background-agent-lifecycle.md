# Background-agent lifecycle - hand back, salvage, stop; and never touch a peer session

**The rule (owner, 2026-11-07).** A dispatched background agent ends when its purpose is done; the dispatcher stops it at once; the leader inherits whatever was left. Sessions that are not ours are never stopped unless the owner says so.

**Why.** The leader's footer showed 4 subagents and 23 shells "running" about 1h20m after each agent had handed back. The agents were idling on "Polling for HW-RUN DONE" and "Waiting for nnl2.out". `ListAgents` said "completed", but the harness holds a finished agent (and its shell tasks, which were no longer OS processes) until the leader calls `TaskStop`. Idle holders are footer noise, wake on stray messages and keep their worktree claims looking alive. Composes with `dont-block-on-background.md` (the leader must not idle-poll either).

## The four legs

1. **Agent side - the hand-back is the LAST act.** No polling, sleep loop, `until grep` wait or run-log wait after it (and none instead of it). Waiting on something you cannot finish (a hw-admission slot, a CI run, a peer)? Name that leftover in the hand-back and end. Standing text: `.claude/agents/product-engineer.md` §4.
2. **Dispatcher side - on every hand-back: salvage, then `TaskStop` that agent immediately**, not at session end. Salvage = work (commits/branch/pointer) + learnings, the legs in `learn-before-archive.md` "Stopping an agent or session is a teardown too" (landing via `feat/methodology-agent-stop-salvage`; link, do not copy). Procedure: `.claude/skills/noc-branch-dispatch/SKILL.md` step 5b.
3. **The leader takes over leftovers** (an unfinished verdict, a pending push, a queued run): it runs, files or tracks them itself (`release_steward action=request`, a pointer note, a reminder). Leftovers are never parked in an idle agent.
4. **Never stop another SESSION.** Peer sessions run in the owner's environment. "End idle agents" means YOUR OWN dispatched agents and shells only; stopping, steering or re-scoping a peer needs the owner's say-so. Informing a peer is allowed and encouraged (`orchestration-craft-canon.md` §6.13), and a notice is information, not a stop order: each session/agent decides how to proceed in its own environment and does not pause for the owner because of it. If the notice reveals a conflict or error, silence is not OK: reply to the sender/steward and resolve it together (`orchestration-craft-canon.md` §6.13).

## Waiting and ending (decision 2026-11-10: `project-history/assistant-chatbot/queue-lifecycle-decision.md`)

- **Waiting (live when D1 lands).** A subagent with a queued delivery hands back, names it as the leftover and ends; it never polls. A top-level session with a pending delivery keeps building and does ONE `release_steward action=mine` per 15 min, riding the owner's load-check cadence (no loop agent), plus at natural checkpoints.
- **Ending (not live until builds 3+5: rebased-twin cleanup fix, end predicate in `mine`).** A session/agent ends ITSELF only when the `mine` end predicate is true (all requests LANDED, plus DEPLOYED if asked, or ejected-with-transfer; no open `mq/*` ref; no unlanded rescue of its slug; no depended-on CI run in flight). Teardown goes LAST: it salvages its own worktrees through `task_branch landed confirm=True` as the final act, never while a CI run it depends on is in flight (a salvage once cancelled the CI it waited on). Worktrees of dead requesters go to the steward / mole sweep. Ejection handling: `release-steward.md` § 7a.

## Backstop - `claude-guard-background-agent-idle.py` (advisory, never stops anything)

- **Events:** `PostToolUse` (all tools) and `UserPromptSubmit`, registered in `.claude/settings.json`. A task-notification (the hand-back) wakes the leader into tool calls, so PostToolUse is the event that reliably runs while the leader is acting; it throttles to one scan per 45 s per session.
- **Data source (verified 2026-11-07 on 33 real transcripts):** `/private/tmp/claude-<uid>/<project>/<session-id>/tasks/<agentId>.output` is a symlink to `~/.claude/projects/<project>/<session-id>/subagents/agent-<agentId>.jsonl`; `agent-<agentId>.meta.json` beside it carries `"finished": true` once the run ended (running agents have no such key). The hand-back may be a `SubagentHandback` tool_use or a final text turn, so the meta flag, not the transcript tail, is the signal. Agents that kept working after hand-back (polling, run-log waits) show up as appended rows after the hand-back.
- **Report:** an agent of THIS session (the tasks dir is keyed by the payload's `session_id`; a peer is never seen) that is `finished`, quiet for 3 min and not already `TaskStop`ped in the leader transcript is named in `additionalContext`, once, re-reminded every 20 min. Hooks firing inside a subagent skip.
- **Fail open, fast (<2 s):** any error is a silent no-op with a stderr line. It is not `primary-write` (fail-closed, 8 s): a lifecycle advisory must never wedge the leader.
- **Telemetry:** one row per reported agent in `guard-events.ndjson` (gitignored, under the primary's .claude/cache) (`guard=background-agent-idle`, `agent_id`, `idle_s`); recurrence = `jq -r 'select(.guard=="background-agent-idle")' guard-events.ndjson | wc -l`. Falling to ~0 is the success measure; a persistent count means the dispatcher step is skipped.
- **Limits:** TaskStop outcomes are not observable beyond the leader transcript; a stopped agent is recognised only by its `TaskStop` line (the transcript path must be in the payload). Delivery of PostToolUse `additionalContext` to the leader is the documented hook contract but was not observable from inside this build; the stderr line is the fallback and the telemetry counts regardless.

## Background processes - they end AT RUNTIME (owner decisions 2026-11-14)

**Measured problem.** 8 cores / 8 GB, 5 GB of swap, load ~130: sessions left retry/poll loops (`until grep ...; sleep`), stuck deliverable checks and test runs whose owner went away; 11 zsh poll loops ran 16-17 h; one retry script ran 4 h unnoticed. An idle watcher (45 min without CPU or output) was REJECTED: any lifetime cap or idle timer can kill long in-flight work. **There is no max lifetime, no idle timer and no auto-report of idle processes anywhere** (a test pins that). The second owner correction: "should be killed as soon as its done, not caught by wrap up commands ... they live no longer than they were meant to, instead of being swept on a command someone remembers to call." **The end happens at runtime; the session-end sweep is a backstop only, and every process it has to stop is counted as an escape (a bug in the legs below).**

**Executors (standing protocol `product-engineer.md` §4, inherited by every executor): a long run goes to `run_in_background`; end your turn; the completion notification resumes you; never wait in a loop.** Subagents have no `TaskStop`, so a waiter they start cannot be stopped by them; the guard's poll refusal is the backstop that makes the rule hold.

**The rule.** Every background process ends the moment its job is done or can no longer finish. Scope is only this session's own `run_in_background` shells and their child trees, never a session, never a peer's processes.

| Leg | Mechanism |
|---|---|
| Mandatory wrapper | PreToolUse guard `bg_launch_guard.py`, wired through the ONE rewrite hook `claude-guard-bash-rewrite.py` (see Rewrite chain below): EVERY `run_in_background` Bash that is not declared infrastructure is **rewritten** (`updatedInput`) into `scripts/bg_run.py --purpose <derived from description or command> --done "the command exits" --command=<cmd>`, not denied. Denied only what cannot be made to end: a loop/follow/watch with no end condition (`while true; do work; done`, `tail -f`, `watch`, `--watch`), and **every poll**, a wrapper without `--purpose` / `--done` (or `--long-lived`), a wrapped open-ended command without `--done-when`. Known infrastructure (`core.INFRA_PATTERNS`) is untouched. Fail-closed (`[noc-guard:background-launch]`); enforcing (`bg_launch_guard.ENFORCE_FROM` = 2026-11-14, `NOC_BG_LAUNCH_MODE=shadow` logs a `warn` and rewrites nothing). Denies and rewrites are logged (`guard=background-launch`, `outcome=deny|rewrite`). |
| Rewrite chain (2026-11-14) | Two hooks that both return `updatedInput` run in PARALLEL on the ORIGINAL input and one rewrite wins, so a background heavy command lost a wrap. ONE hook, `claude-guard-bash-rewrite.py` -> `bash_rewrite_chain.decide`, applies them in a fixed order: the heavy-run wrap is INNERMOST (`hw_admission.py run`), the `bg_run.py` wrap OUTERMOST, i.e. `bg_run.py ... --command='<venv python> hw_admission.py run ... -- bash -c <cmd>'`: the process tree ends at runtime AND admission still queues the heavy work. Idempotent (already-wrapped input is returned unchanged), a deny from either member guard wins over any rewrite and keeps that guard's marker, each rewrite logs its own event (`guard=heavy-run` / `guard=background-launch`, `outcome=rewrite`). Never wire a second `updatedInput` hook on `Bash`: add the step to the chain. Deadline overrun (kept from the retired hook, tested in `test_bg_process.py`): in `NOC_BG_LAUNCH_MODE=shadow` a timeout is allowed (logged `allow-timeout`) unless the command could hold a heavy run; in enforce (default) every timeout denies. Limit: a heavy command inside a hand-written `bg_run.py` wrapper is not looked into. |
| No polling (owner ruling 2026-11-14) | A POLL is a `while`/`until` whose body is only `sleep` + a readiness test (file exists/non-empty, grep a pattern, pgrep). It is denied foreground AND background, **bounded by `timeout N` or not** (`timeout 590 bash -c 'until [ -s <tasks>/<id>.output ]; do sleep 10; done'` was the shape 13 agent loops used). Deny text: "launch the command itself with run_in_background; the completion notification resumes you; read a task output once, never in a loop". Bounded non-poll loops (`for f in ...; do ...; done`, `timeout N` around a loop that does work) stay allowed. |
| Structure, not text | `scripts/hooks/_bg_shell.py` lexes the command like a shell (quotes, `$(...)`, backticks, comments, heredocs, redirections; hand-written, **no new dependency**: bashlex is not vendored). Quoted text is DATA unless something executes it (`bash -c STR`, `eval`, `$(...)`, a heredoc fed to a shell); a heredoc body written to a file (`cat > f <<EOF`) and prose in `-m '...'` are never judged; a `while`/`until` is a loop only at a command start with a closing `do ... done`; `while read` / `getopts` / `[ $# ... ]` are bounded by their input; `timeout N` (also inside `-c`) and `bg_run.py --done-when|--long-lived` bound what they wrap. |
| Scripts | The first path token of an invoked script (`./poll.sh`, `bash x.sh`, `python poll.py`, after a `cd`) is opened when it is a readable file under the repo or the session scratchpad, <= 128 KB, <= 6 files, <= 4 levels, and scanned the same way (shell: the same structure; Python: `ast`, only an infinite `while True` with no break/return/raise). Judged in the background AND in the foreground. |
| Foreground | The harness moves a foreground call that hits the 600 s tool timeout to the background by itself, so an unbounded loop/follow/watch is denied without `run_in_background` too, inline or inside an invoked script. A bare foreground `sleep N`, test runs and prose are not judged. The deny teaches: launch the run itself with `run_in_background` and wait for its notification, do not poll its log; bounded = `timeout N` or the wrapper with `--done-when`. Hook fast path: a call with no loop keyword, `--watch`, script suffix or `./` skips the module load. |
| Wrapper ends it | `bg_run.py` ends when the command exits OR `--done-when` succeeds; then tree-stops the command's process group (own session, so orphans re-parented to init are still found), verifies none survives, writes its own salvage record. A looping command without `--done-when` is refused by the wrapper itself. |
| Dead-producer end | A wrapped wait whose `--done-when` watches a file (absolute or relative `*.log|out|output|txt`) ends itself (rc 4, salvage `done-when can never fire`) when the producer is provably gone: no process holds the file open for write, its producer pid (`--producer-pid`, else the writers observed) is dead, the file is unchanged, over 3 consecutive checks. A done-condition, not a timer: never fires while anything that could still write is alive. |
| Parent-death | When the wrapper runs under a Claude session it ends its tree (rc 5, salvage `owning session ended`) the moment the owner is gone: the `claude` pid it found at start no longer exists (checked every 5 s from `ps`), or it was re-parented to init (its shell died; only if it did not start detached). A wrapper outside a Claude session has no owner and is not subject to it. Orphans cannot exist by construction. |
| Backstop + escape count | `noctus.dev.session_end_sweep` lists this session's still-running background processes (`background_processes`); `clean_wrap` is False until each is salvaged + stopped via `noctus.dev.bg_process action=stop` or kept as declared long-lived. Every process `stop` has to stop is logged as `guard=background-process outcome=escaped-runtime-end`: an escape is a bug in the legs above (a launch shape the guard missed, a wrapper that did not end). Count: `jq -r 'select(.outcome=="escaped-runtime-end")' guard-events.ndjson | wc -l`; the success measure is ~0. |
| Stop tool | `noctus.dev.bg_process` (`--bg-process`): `list` / `declare` / `undeclare` / `salvage` / `stop`. `stop` REFUSES to signal until a salvage record exists (output tail saved outside git, in the gitignored per-machine cache dir, reason, learnings), then TERM root-first, wait, KILL survivors, verify no orphans. Refuses a peer's pid, infrastructure, live declarations, and its own claude chain. |
| Telemetry | `guard-events.ndjson` rows (`guard=background-launch` deny/rewrite/warn; `guard=background-process` salvaged/stopped/escaped-runtime-end), salvage records (ndjson) and the wrapper run logs. |

**Ownership signals (verified 2026-11-14).** Hooks and the MCP server find their session's `claude` process by walking up from their own pid; background shells are its children; a detached shell counts only when its command carries `/<session_id>/`. "Parent is pid 1" alone is never an orphan test (the steward's watchers detach on purpose). Stdout of a task shell is often a socket or `/dev/null`, so the output file is mapped only when a task `.output` is open; otherwise the dossier says so.

**Limits.** A loop assembled at runtime (`eval "$VAR"`, a script generated then sourced), a script larger than 128 KB or outside the repo and scratchpad, and a Python `while` that is not a constant-true infinite loop are not seen; a wait on a file that does not exist yet cannot be watched for its producer (parent-death still ends it). The wrapper runs the command with `/bin/sh -c`, not the user's interactive shell. The sweep catches the rest and counts it.

**Fix-on-contact (same change).** `claude-guard-background-agent-idle.py` re-reported agents whose `TaskStop` returned `No task found with ID`; that error result now counts as stopped.

Tests: `mcp/noctusai/tests/test_bg_process.py` (fake `ps` + fake kill; never a real signal; scripts and structure on real temp files).
