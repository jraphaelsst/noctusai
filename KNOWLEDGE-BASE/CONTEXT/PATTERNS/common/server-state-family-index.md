# Frontend server state — family index (§1 consolidation)

> **Family-line pattern:** CLAUDE.md §1 carries ONE line for this family; the member rules live here **verbatim**. This is a lossless MOVE, not a summary — the bytes below are the bytes that were in §1. Each member keeps its own depth doc; this index is the router hop between the §1 family line and those docs. Consolidated 2026-10-21 (adding the cache-writes rule took §1 to 56 against a cap of 55). → `KB § PATTERNS/common/methodology-gc.md`

All four rules answer one question: **does what the screen shows agree with the server right now?** The first governs READS (what to render while data is pending or refetching); the second governs WRITES (what the cache holds between the click and the server's answer — every entry the write touches, and a queued job until it settles); the third governs FAILURES (a no from the server is shown as a no — never as an empty list, never as nothing); the fourth governs DRAFTS (a value on screen the server does not have yet). Rules three and four were added 2026-10-24 as family members, not new §1 lines. A product that follows one and not the others still shows the user something false.

## Members (verbatim from §1)

- **No lying loading states — two signals, never `isLoading`: `showSkeleton = isPending && !data`, `isRefreshing = isFetching && !!data`.** `isLoading` is false mid-refetch so an empty branch lies over data; a bare `isFetching` gate unmounts content that exists (70 sites, 2026-08-31); key-change queries need `placeholderData`; keeper `check_lying_loading_state` covers the first mode only. → `KB § PATTERNS/frontend/lying-loading-state.md`
- **A write puts what it knows into the cache — never invalidate-only.** Invalidate-only throws away the server's answer: the screen contradicts the toast for write + refetch (orbity note ~2 s, 2026-10-21; 94% of fleet mutations). `useCacheWriteMutation` / `createCrudHooks`; keeper `check_mutation_invalidate_only` (ratchet). → `KB § PATTERNS/frontend/mutation-cache-writes.md` · skill `noc-cache-writes`
  - **…into the right entries (2026-10-24).** An exact `setQueryData` refreshes the key's derived family too (keeper `check_mutation_family_write`, family derived from the key convention), and a job-starting write hands off to the polled read with `handOffToPolling` (keeper `check_job_start_without_handoff`). → `KB § PATTERNS/frontend/mutation-cache-writes.md` § Write the family · § Async jobs hand off
- **A refusal is never silent — a failed query never reads as "nothing found", an upload refusal is always on screen with the file name.** `?? []` makes "failed" and "empty" the same value (F76: 502 → "Nenhum imóvel" + "Cadastrar novo"); a `void` `onUpload` drops the rejection (F78, F86, F75b — 2026-10-24). `QueryErrorState` first; uploads via `useUploadDocumento` + `<UploadErro>` (`@noctusai/lib/upload-refusal`); keeper `check_silent_refusal`. → `KB § PATTERNS/frontend/silent-refusal.md`
- **A draft says it is unsaved.** A value shown but not yet persisted reads as applied and is lost on reload (social-wiring F91, 2026-10-24); no precise static rule exists, so the mechanism is the seed organ `useUnsavedChanges` + `<UnsavedChangesNotice>` (and `useBeforeUnloadGuard`), adopted in every inline multi-field Salvar card. → `KB § PATTERNS/frontend/mutation-cache-writes.md` § Drafts say they are unsaved

## Why a family line

A session writing a TanStack hook needs both: the write contract's background settle is a refetch, and rendering that refetch honestly is the loading-state rule. One router hop returns one always-on line of budget. The forcing function is the router keeper's rule-COUNT ceiling; the procedure is `/gc` step 5. → `KB § PATTERNS/common/claude-md-router-discipline.md`
