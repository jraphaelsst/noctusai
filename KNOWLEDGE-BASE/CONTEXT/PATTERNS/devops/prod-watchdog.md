# Prod watchdog — off-host liveness check + on-host heartbeat

> `noctus.dev.prod_watchdog` · `cli.py --prod-watchdog` · `.github/workflows/prod-watchdog.yml` · `deploy/watchdog/`

## 1. Why (2026-10-11)

At ~01:17Z the prod VPS (8 GB RAM, 2 vCPU, 2 GB swapfile added that day) hard-froze right after a fleet deploy: no ping, no SSH, Cloudflare **530** on every site, until the owner rebooted it by hand. The post-mortem found that **host journald and cron/sysstat had stopped ~20h earlier** while the sites kept serving — the host was dying in silence for most of a day.

Two lessons shape the design:

- **An on-host check dies with the host.** Anything that runs on the VPS (cron, a systemd timer, a container) went quiet at the same moment as everything else. The checker must run **elsewhere** — GitHub Actions, every 10 min.
- **"Sites serving" ≠ "host healthy".** HTTP alone would have stayed green for those ~20h. The checker must also read **host-internal liveness** — and it needs an on-host signal designed to go stale when the host's own scheduling stalls: the **heartbeat**.

## 2. Architecture

```
GitHub Actions (cron */10)                         prod VPS
┌──────────────────────────────┐   HTTPS (CF)   ┌───────────────────────────────┐
│ prod_watchdog.py (stdlib)    │ ─────────────▶ │ core + build-scope products   │
│  http_probe  /api/health ×N  │                │   /api/health (+ core `/`)    │
│  host_probe  ONE ssh call    │ ─── ssh ─────▶ │ authorized_keys: restrict,    │
│  classify → up|degraded|down │  forced cmd    │  command=host-probe.sh        │
│  dedupe state (Actions cache)│ ◀── 1 JSON ─── │ noctus-heartbeat.timer (5min) │
│  alert: Resend / WAHA        │                │  → /var/lib/noctus/heartbeat  │
└──────────────────────────────┘                └───────────────────────────────┘
```

- **Roster** — `core` + every slug in `deploy/fleet/build-scope.txt` (regenerated by `sync-product-scope.yml`; no credentials needed). **Hostnames** from `deploy/tunnel/ingress.yml` via `_public_edge.public_hostname` (shortest route wins, so core → apex `noctusai.com`).
- **Shared stdlib module** — the browser UA (CF WAF 1010), the never-raising `fetch`, the roster reader and the ingress parser live in `mcp/noctusai/tools/noctus/dev/_public_edge.py`, imported by **both** `spa_smoke` and `prod_watchdog`. It must stay stdlib-only: the CI job runs `python -m tools.noctus.dev.prod_watchdog` with **no pip install**. The ingress line parser is held to parity with `yaml.safe_load` on the real file by a test, so a shape change fails CI instead of resolving a wrong host.
- **host_probe** — `deploy/watchdog/host-probe.sh` prints ONE JSON line: `journald_last_age_s`, `heartbeat_age_s`, `mem_available_mb`, `swap_used_mb`, `load1`, `load5`, `ncpu`, `uptime_s`, `now`. It is read-only, `set -u` (never `-e`), every read time-boxed; anything it cannot read becomes `null` — a missing answer **is** the signal. The parser takes the last JSON-object line and coerces each field to number-or-null.
- **Heartbeat** — `noctus-heartbeat.timer` (`OnBootSec=1min`, `OnUnitActiveSec=5min`) fires a oneshot that writes the epoch to `/var/lib/noctus/heartbeat`. A stale heartbeat with healthy HTTP = the host's scheduling has stalled, the precursor shape of 2026-10-11.

## 3. Classification

Thresholds are module constants in `prod_watchdog.DEFAULTS`, each overridable by the env var of the same name.

| State | When |
|---|---|
| **DOWN** | core HTTP (`/api/health` or `/`) failing **2 consecutive runs** · or SSH unreachable 2 runs **and** core impaired this run (failing, or `startup_hook_error`) |
| **DEGRADED** | SSH unreachable 2 runs with HTTP fine · journald last entry > 30 min (or none) · heartbeat > 15 min or missing · MemAvailable < 600 MB · swap used > 1024 MB · load1 > 2×ncpu · a non-core product failing 2 consecutive runs · any product reporting `startup_hook_error` · host-probe output unreadable |
| **UP** | none of the above |

A failure is: connection error (status 0), any non-2xx (incl. CF 530/52x). **A single blip never alerts** — every failure-type reason needs `WATCHDOG_CONSECUTIVE` (2) consecutive runs. `ssh` exiting 255 is "unreachable"; any other exit with no parseable JSON is a probe error (host reachable → the SSH counter resets).

## 4. Dedupe + routing

State file (Actions cache, `prod-watchdog-state-<run_id>`, restored by prefix): `state`, `since`, `alerted_state`, `last_alert_at`, per-check consecutive `counters`, and the SSH backoff.

- **Alert only when the classified state differs from `alerted_state`** — the last state the owner was *successfully* told about. Recovery to `up` is a state change and alerts too.
- **Reminder** every `WATCHDOG_REMINDER_HOURS` (6) while not up. Never a message per run.
- An alert that reached **no** channel leaves `alerted_state` untouched (retried next run) and exits 1.

| Kind | Channels |
|---|---|
| DOWN | email (Resend); WhatsApp also tried, best-effort |
| DEGRADED | WhatsApp (WAHA); falls back to email if WAHA fails or is not configured |
| RECOVERY | both, where available |

Messages are short pt-BR (`[NoctusAI prod] FORA DO AR / DEGRADADO / RECUPERADO / LEMBRETE`), list the reasons and a UTC timestamp, and never carry a host, IP or secret (ssh stderr is redacted in the report and never enters a message). A missing channel is a loud `WARNING` every run; **with `--send` and no channel configured the run exits 1** (workflow red). Red therefore means *the watchdog cannot alert* — prod's own state goes out over email/WhatsApp. `workflow_dispatch` input `send_test_alert` pushes a TEST message through every configured channel and goes red if any configured channel fails.

## 5. SSH: one connection, backoff, restricted key

fail2ban runs sshd with `maxretry=5`, `findtime=600`. The same circuit-breaker idea as `_vps_ssh.py`, adapted to stateless CI runs:

- **Exactly ONE authenticated ssh connection per run** (`StrictHostKeyChecking=yes`, `ConnectTimeout=20`, `BatchMode=yes`), preceded by `ssh-keyscan` with 3 tries (a pre-auth handshake; not an auth failure).
- **Backoff across runs**, persisted in the state: below 3 consecutive SSH failures every run connects; then every 2nd run, every 3rd, … capped at every 6th (1h at a 10-min cron). Skipped runs keep the failure count, so the state stays DEGRADED/DOWN.
- **Restricted key** — the full prod key never enters CI (`vps.py` doctrine). A NEW key, secret `NOCTUS_VPS_WATCHDOG_KEY`, whose `authorized_keys` line is:
  ```
  restrict,command="/opt/noctus/noctusai/deploy/watchdog/host-probe.sh" ssh-ed25519 AAAA… noctus-prod-watchdog
  ```
  `restrict` (no pty, no port/agent/X11 forwarding, no user-rc) is the right form here because this key needs **no** forward — the `restrict`-vs-`permitopen` trap in `KB § PATTERNS/devops/ssh-deploy-key-restrictions.md` only bites when a `permitopen` hole is wanted. `$SSH_ORIGINAL_COMMAND` is ignored.

## 6. Secrets and variables (names only)

| Name | Kind | Purpose |
|---|---|---|
| `NOCTUS_VPS_HOST` | secret | VPS address (shared with deploy-prod) |
| `NOCTUS_VPS_WATCHDOG_KEY` | secret | the restricted private key (§5) |
| `RESEND_API_KEY` | secret | email via `POST https://api.resend.com/emails`, from `NoctusAI <noreply@noctusai.com>` |
| `WAHA_BASE_URL` · `WAHA_API_KEY` · `WAHA_SESSION` | secrets | WhatsApp via `POST {WAHA_BASE_URL}/api/sendText` (`X-Api-Key`); session defaults to `default` |
| `WATCHDOG_ALERT_WHATSAPP` | secret | recipient digits (`<digits>@c.us`) |
| `WATCHDOG_ALERT_EMAIL` | variable | recipient; the workflow defaults it to the owner's address (owner's choice), swappable by setting the repo variable |

Missing host/key → the SSH leg is skipped with a warning; HTTP checks and alerting still run.

## 7. Install (on the VPS, as root)

```bash
cd /opt/noctus/noctusai                       # after the bless that ships deploy/watchdog/
ssh-keygen -t ed25519 -N '' -C noctus-prod-watchdog -f /root/watchdog-key   # or generate off-host
bash deploy/watchdog/install-heartbeat.sh --watchdog-pubkey /root/watchdog-key.pub
bash deploy/watchdog/install-heartbeat.sh --check --watchdog-pubkey /root/watchdog-key.pub
# put the PRIVATE key into the GitHub secret NOCTUS_VPS_WATCHDOG_KEY, then delete it from the host
```

`install-heartbeat.sh` is idempotent: copies the units into `/etc/systemd/system` only when content differs, `daemon-reload` only after a change, `systemctl enable --now noctus-heartbeat.timer`, creates `/var/lib/noctus`, and adds the key line exactly once (matched on the key body). `--check` changes nothing and also runs the probe once. Then run the workflow by hand with `send_test_alert: true` to prove each channel.

Local dry probe (sends nothing, no state): `python mcp/noctusai/cli.py --prod-watchdog` (add `--watchdog-state F`, `--send`, `--watchdog-test-alert`, `--json`).

## 7b. Supabase request budget + fleet breaker (added 2026-11-10)

> Telemetry + stop leg of `KB § PATTERNS/backend/polling-request-budget.md`. Same run, same state file, same alert routing.

- **Sensor** — `noctus.dev.supabase_request_budget` (`cli.py --supabase-request-budget`), stdlib-only, imported by this module. Reads the project's OWN edge logs: Management API `GET /v1/projects/{ref}/analytics/endpoints/logs` (ClickHouse SQL, `iso_timestamp_start/end`, 24 h max; `logs.all` is 410 Gone) plus `usage.api-counts`. The v1 API has **no org egress/quota figure**: the budget is judged on request volume.
- **What can trip it (security review F1).** `edge_logs` also records anonymous, key-less and rejected requests, so anyone hammering the public project URL must not be able to stop the fleet. **Only traffic carrying OUR service_role key** counts toward **critical**, and the role claim alone is NOT an identity: edge_logs records the DECODED header, so a forged `service_role` is logged too, and some answers come before key-auth (CORS OPTIONS preflight, `/auth/v1/verify|authorize|callback` 3xx, functions with `verify_jwt=false`). Trip traffic is therefore `role = service_role` **AND path starts `/rest/v1/` AND method != OPTIONS AND status 2xx/3xx** (PostgREST verifies the JWT signature: a forged key gets 401 there and is excluded), plus service_role 402s on the same filter. **Optional signature pin (recommended):** every service_role call on `/rest/v1` carries the same `request.sb.jwt.apikey.payload.signature_prefix` in the logs; a forger can write any signature segment but cannot know ours. Set the GitHub secret `SUPABASE_SERVICE_SIG_PREFIX` (validated `[A-Za-z0-9_-]{4,16}`, never printed: reports say only `signature pin: on|off`) and trip traffic must also carry it. Read it ONCE from the Logs Explorer: `select distinct log_attributes['request.sb.jwt.apikey.payload.signature_prefix'] from logs where source='edge_logs' and log_attributes['request.sb.jwt.apikey.payload.role']='service_role' and log_attributes['response.status_code']='200' limit 5` (one value; if there are several, our key was rotated). The trip decision comes from ONE ungrouped `countIf` aggregate, not from the UA×status `LIMIT` grouping (which a spray could crowd out; that grouping is reporting only). Anon / authenticated / key-less / 4xx-5xx traffic is reported and can **warn**, never trip.
- **Verdict** (per-day projections; env `SUPABASE_BUDGET_{WARN,CRIT}_{TOTAL,SHAPE}_PER_DAY`): **critical** = our traffic > 250k total · one of our shapes > 50k · a service_role `/rest/v1` 402 **wave** (>= `SUPABASE_BUDGET_MIN_402_TO_TRIP`, default 100 per window: one forged 402 never trips); **warn** = > 100k (any traffic) · a shape > 15k; **unknown** = logs unreadable (never green, never red).
- **LGPD / public logs (F8).** The repo is public, so the run log and the state cache carry **counts and verdicts only**. Endpoint **shapes** (path allowlist `/{rest|auth|storage|functions}/v1/<known first segment>`, filter values/ids/filenames -> `?`) go only into the **email body**; WhatsApp and stdout never get them.
- **Policy per run** (each needs `WATCHDOG_CONSECUTIVE` runs; a 402 wave trips at once): warn -> alert only (DEGRADED); critical -> **trip the fleet breaker** + alert; unknown/unconfigured -> a warning, never a trip, **but `WATCHDOG_BUDGET_BLIND_RUNS` (6) consecutive blind runs go DEGRADED** (an expired/revoked token must not silently remove the protection).
- **Breaker** — Redis key `noctus:breaker:fleet` = JSON `{reason, rate, window, tripped_at, by:"offhost-watchdog"}`, no TTL. While it exists every product's workers/schedulers stay stopped and the APIs keep serving (seed side: `feat/supabase-breaker`). The watchdog sets it through ONE ssh call to a **separate forced-command key** running `deploy/watchdog/breaker-trip.sh`: it validates the exact shape, re-serialises it, does `SETNX` (the first trip's reason stands; the ACL `trip` user holds `+setnx` only, so it can neither overwrite nor expire the key) and can do nothing else, never delete. The trip is **re-asserted on every critical verdict** (NX makes it idempotent), so a re-arm never leaves the leg blind.
- **State vs reality (F6).** `host-probe.sh` reports `breaker_tripped` (`EXISTS noctus:breaker:fleet`). Key gone => a human re-armed => the sticky alert clears by itself; key present with no state => adopted and alerted once; unreadable => nothing changes. Never auto-re-arms: re-arm is `noctus.dev.supabase_breaker`; `--breaker-rearmed` stays as a manual override.
- **Least privilege on the VPS (F12).** The trip key logs in as a dedicated unprivileged user `breaker` (not root) whose only power is a sudoers entry for exactly `breaker-trip.sh` with no arguments, run with `env_reset`; the read-only probe key follows the same pattern with an unprivileged `probe` user and a sudoers entry for exactly `host-probe.sh` (set `WATCHDOG_PROBE_USER=probe` once it exists; unset = legacy root, so nothing breaks mid-migration) (chosen over `docker` group membership, which is root-equivalent, and over a shell wrapper with `docker exec` rights). `host-probe.sh` also reports `breaker_key_restricted`: every authorized_keys line carrying `noctus-prod-watchdog` / `noctus-breaker-trip` must start with `restrict,command="`, else the watchdog goes DEGRADED.
- **Redis target.** (`host-probe.sh` prefers a read-only `probe` ACL user from `probe.pass` when that file exists and falls back to `trip.pass`.) `breaker-trip.sh` and `host-probe.sh` use today's unauthenticated `noctus-redis`; once `/opt/noctus/noctusai/deploy/fleet/redis-auth/trip.pass` exists (the `redis-acl-lockdown` doc §5, branch `feat/redis-acl-lockdown`, landing later) both switch to `noctus-breaker-redis` as user `trip`, the password passed through the environment (`docker exec -e REDISCLI_AUTH`), never a command line.
- **Pinned host key.** `NOCTUS_VPS_KNOWN_HOSTS` (secret; output of `ssh-keyscan -H <host>` captured once, `-H` hashes the host so the public repo does not learn the IP) is the trust anchor for BOTH keys. Unset, `_ssh_once` falls back to a keyscan on every run (trust-on-first-use each time) and the run warns loudly.

**Owner setup (nothing here installs itself):**

1. **Scoped Supabase token** (secret `SUPABASE_ACCESS_TOKEN`; optional variable `SUPABASE_PROJECT_REF`). Do NOT use an account-wide PAT in a public repo's workflow: create a *scoped access token* limited to project `nyplttplcoyiiqjrvtiw` with only the observability reads these endpoints require (per the Management API spec: `analytics_logs_read` for `/analytics/endpoints/logs` and `analytics_usage_read` for `/analytics/endpoints/usage.api-counts`; OAuth equivalent `analytics:read`). If the dashboard labels differ, pick "Logs: Read" and "Usage Analytics: Read"; nothing else. The token reaches only the single "Run the watchdog" step.
2. **GitHub Environment (recommended).** Create the environment `prod-watchdog` (the workflow already declares `environment: prod-watchdog`) and **restrict its deployment branches to `main`** (Settings -> Environments -> prod-watchdog -> Deployment branches and tags -> Selected branches -> add `main`). The run report flags `environment protection: unknown/off` when this cannot be confirmed (it can only be read with an optional `WATCHDOG_GH_TOKEN` that may read the repo's environments; the report never fails over it), and move `NOCTUS_VPS_BREAKER_KEY`, `SUPABASE_ACCESS_TOKEN`, `NOCTUS_VPS_WATCHDOG_KEY`, `RESEND_API_KEY` and the `WAHA_*` secrets into it. Without it the secrets resolve from the repository and the workflow still runs. Every secret is step-scoped either way.
3. Optional secret `SUPABASE_SERVICE_SIG_PREFIX` (see the sensor bullet). Secrets `NOCTUS_VPS_BREAKER_KEY` (private half of a NEW ed25519 key) and `NOCTUS_VPS_KNOWN_HOSTS` (`ssh-keyscan -H <host>`, captured once).
4. **On the VPS**, as root:
   - `useradd -m -s /bin/sh breaker`. The shell MUST be able to run a command: sshd executes the forced command through the user's login shell, so `/usr/sbin/nologin` refuses it and every trip would fail. `restrict` + `command=` (and the sudoers entry) are what confine the key, not the shell. No password, no docker group.
   - `install -m 0440 -o root -g root deploy/watchdog/noctus-breaker.sudoers /etc/sudoers.d/noctus-watchdog && visudo -cf /etc/sudoers.d/noctus-watchdog` (the file holds the `breaker` and `probe` entries).
   - `/home/breaker/.ssh/authorized_keys` (**`root:root` 0644, in a `root:root` 0755 `.ssh` directory**, so `breaker` cannot edit its own forced command; sshd StrictModes accepts a root-owned file there):

```
restrict,command="sudo /opt/noctus/noctusai/deploy/watchdog/breaker-trip.sh" ssh-ed25519 AAAA...pubkey... noctus-breaker-trip
```

   - **One-time verification, without tripping the fleet** (the `verify` payload is a read-only `EXISTS`):

```
echo '{"verify":true}' | ssh -i breaker-key breaker@<host>      # expect {"verify":true,"exists":0}
```

     `exists:0/1` proves ssh + forced command + sudo + redis access. `invalid payload` means the chain is up but the script refused; a `sudo`/`Permission denied` message means the sudoers entry or the script ownership is wrong. `host-probe.sh` then reports `breaker_key_restricted: 1`.
5. **Probe key hardening (optional, do after 4).** `useradd -m -s /bin/sh probe`, install its key with `NOCTUS_PROBE_USER=probe bash deploy/watchdog/install-heartbeat.sh --watchdog-pubkey k.pub` (fails loudly up front if the user is missing or has a `nologin` shell, makes the file `root:root` 0644, and writes `/home/probe/.ssh/authorized_keys` with `restrict,command="sudo .../host-probe.sh"`), then set the repository variable `WATCHDOG_PROBE_USER=probe` and remove the old root line.

   Without (1) the leg reports `not_configured` (and DEGRADED after 6 runs); without the breaker key a critical still alerts and says it could not trip.

## 8. Limits (named, so nobody trusts it for what it does not check)

- **GitHub cron is best-effort** — ticks can be delayed by many minutes or skipped under load; "every 10 min" is a target, and DOWN needs 2 runs, so detection latency is ~20 min at best and can be longer.
- **Schedules fire only from the default branch (`main`)** — the watchdog goes live at the next bless, not at merge to `dev`. Until then, run it by hand (`workflow_dispatch`) or locally.
- **WAHA runs on the VPS** — when the host is down WhatsApp is down too. That is why DOWN routes to email first; DEGRADED (host still up) prefers WhatsApp.
- **Not a metrics system** — it reads point-in-time values every 10 min; a spike between runs is invisible. Its job is "is the host alive and still keeping time", not capacity planning.
- **State lives in the Actions cache** — if the cache is evicted the watchdog starts fresh (counters reset; a still-bad state alerts again once). Each run prunes its own superseded `prod-watchdog-state-*` caches after saving; `cache-cleanup.yml` would also keep only the newest (the decimal run-id suffix matches its hex-suffix strip).
