# Prod watchdog — off-host liveness check + on-host heartbeat

> `noctus.dev.prod_watchdog` · `cli.py --prod-watchdog` · `.github/workflows/prod-watchdog.yml` · `deploy/watchdog/`

## 1. Why (2026-10-11)

At ~01:17Z the prod VPS (8 GB RAM, 2 vCPU, 2 GB swapfile added that day) hard-froze right after a fleet deploy: no ping, no SSH, Cloudflare **530** on every site, until the owner rebooted it by hand. The post-mortem found that **host journald and cron/sysstat had stopped ~20h earlier** while the sites kept serving — the host was dying in silence for most of a day.

Two lessons shape the design:

- **An on-host check dies with the host.** Anything that runs on the VPS (cron, a systemd timer, a container) went quiet at the same moment as everything else. The checker must run **elsewhere** — GitHub Actions, every 10 min.
- **"Sites serving" ≠ "host healthy".** HTTP alone would have stayed green for those ~20h. The checker must also read **host-internal liveness** — and it needs an on-host signal designed to go stale when the host's own scheduling stalls: the **heartbeat**.

## 2. Architecture

```
GitHub Actions (cron */10)                         prod VPS
┌──────────────────────────────┐   HTTPS (CF)   ┌───────────────────────────────┐
│ prod_watchdog.py (stdlib)    │ ─────────────▶ │ core + build-scope products   │
│  http_probe  /api/health ×N  │                │   /api/health (+ core `/`)    │
│  host_probe  ONE ssh call    │ ─── ssh ─────▶ │ authorized_keys: restrict,    │
│  classify → up|degraded|down │  forced cmd    │  command=host-probe.sh        │
│  dedupe state (Actions cache)│ ◀── 1 JSON ─── │ noctus-heartbeat.timer (5min) │
│  alert: Resend / WAHA        │                │  → /var/lib/noctus/heartbeat  │
└──────────────────────────────┘                └───────────────────────────────┘
```

- **Roster** — `core` + every slug in `deploy/fleet/build-scope.txt` (regenerated by `sync-product-scope.yml`; no credentials needed). **Hostnames** from `deploy/tunnel/ingress.yml` via `_public_edge.public_hostname` (shortest route wins, so core → apex `noctusai.com`).
- **Shared stdlib module** — the browser UA (CF WAF 1010), the never-raising `fetch`, the roster reader and the ingress parser live in `mcp/noctusai/tools/noctus/dev/_public_edge.py`, imported by **both** `spa_smoke` and `prod_watchdog`. It must stay stdlib-only: the CI job runs `python -m tools.noctus.dev.prod_watchdog` with **no pip install**. The ingress line parser is held to parity with `yaml.safe_load` on the real file by a test, so a shape change fails CI instead of resolving a wrong host.
- **host_probe** — `deploy/watchdog/host-probe.sh` prints ONE JSON line: `journald_last_age_s`, `heartbeat_age_s`, `mem_available_mb`, `swap_used_mb`, `load1`, `load5`, `ncpu`, `uptime_s`, `now`. It is read-only, `set -u` (never `-e`), every read time-boxed; anything it cannot read becomes `null` — a missing answer **is** the signal. The parser takes the last JSON-object line and coerces each field to number-or-null.
- **Heartbeat** — `noctus-heartbeat.timer` (`OnBootSec=1min`, `OnUnitActiveSec=5min`) fires a oneshot that writes the epoch to `/var/lib/noctus/heartbeat`. A stale heartbeat with healthy HTTP = the host's scheduling has stalled, the precursor shape of 2026-10-11.

## 3. Classification

Thresholds are module constants in `prod_watchdog.DEFAULTS`, each overridable by the env var of the same name.

| State | When |
|---|---|
| **DOWN** | core HTTP (`/api/health` or `/`) failing **2 consecutive runs** · or SSH unreachable 2 runs **and** core impaired this run (failing, or `startup_hook_error`) |
| **DEGRADED** | SSH unreachable 2 runs with HTTP fine · journald last entry > 30 min (or none) · heartbeat > 15 min or missing · MemAvailable < 600 MB · swap used > 1024 MB · load1 > 2×ncpu · a non-core product failing 2 consecutive runs · any product reporting `startup_hook_error` · host-probe output unreadable |
| **UP** | none of the above |

A failure is: connection error (status 0), any non-2xx (incl. CF 530/52x). **A single blip never alerts** — every failure-type reason needs `WATCHDOG_CONSECUTIVE` (2) consecutive runs. `ssh` exiting 255 is "unreachable"; any other exit with no parseable JSON is a probe error (host reachable → the SSH counter resets).

## 4. Dedupe + routing

State file (Actions cache, `prod-watchdog-state-<run_id>`, restored by prefix): `state`, `since`, `alerted_state`, `last_alert_at`, per-check consecutive `counters`, and the SSH backoff.

- **Alert only when the classified state differs from `alerted_state`** — the last state the owner was *successfully* told about. Recovery to `up` is a state change and alerts too.
- **Reminder** every `WATCHDOG_REMINDER_HOURS` (6) while not up. Never a message per run.
- An alert that reached **no** channel leaves `alerted_state` untouched (retried next run) and exits 1.

| Kind | Channels |
|---|---|
| DOWN | email (Resend); WhatsApp also tried, best-effort |
| DEGRADED | WhatsApp (WAHA); falls back to email if WAHA fails or is not configured |
| RECOVERY | both, where available |

Messages are short pt-BR (`[NoctusAI prod] FORA DO AR / DEGRADADO / RECUPERADO / LEMBRETE`), list the reasons and a UTC timestamp, and never carry a host, IP or secret (ssh stderr is redacted in the report and never enters a message). A missing channel is a loud `WARNING` every run; **with `--send` and no channel configured the run exits 1** (workflow red). Red therefore means *the watchdog cannot alert* — prod's own state goes out over email/WhatsApp. `workflow_dispatch` input `send_test_alert` pushes a TEST message through every configured channel and goes red if any configured channel fails.

## 5. SSH: one connection, backoff, restricted key

fail2ban runs sshd with `maxretry=5`, `findtime=600`. The same circuit-breaker idea as `_vps_ssh.py`, adapted to stateless CI runs:

- **Exactly ONE authenticated ssh connection per run** (`StrictHostKeyChecking=yes`, `ConnectTimeout=20`, `BatchMode=yes`), preceded by `ssh-keyscan` with 3 tries (a pre-auth handshake; not an auth failure).
- **Backoff across runs**, persisted in the state: below 3 consecutive SSH failures every run connects; then every 2nd run, every 3rd, … capped at every 6th (1h at a 10-min cron). Skipped runs keep the failure count, so the state stays DEGRADED/DOWN.
- **Restricted key** — the full prod key never enters CI (`vps.py` doctrine). A NEW key, secret `NOCTUS_VPS_WATCHDOG_KEY`, whose `authorized_keys` line is:
  ```
  restrict,command="/opt/noctus/noctusai/deploy/watchdog/host-probe.sh" ssh-ed25519 AAAA… noctus-prod-watchdog
  ```
  `restrict` (no pty, no port/agent/X11 forwarding, no user-rc) is the right form here because this key needs **no** forward — the `restrict`-vs-`permitopen` trap in `KB § PATTERNS/devops/ssh-deploy-key-restrictions.md` only bites when a `permitopen` hole is wanted. `$SSH_ORIGINAL_COMMAND` is ignored.

## 6. Secrets and variables (names only)

| Name | Kind | Purpose |
|---|---|---|
| `NOCTUS_VPS_HOST` | secret | VPS address (shared with deploy-prod) |
| `NOCTUS_VPS_WATCHDOG_KEY` | secret | the restricted private key (§5) |
| `RESEND_API_KEY` | secret | email via `POST https://api.resend.com/emails`, from `NoctusAI <noreply@noctusai.com>` |
| `WAHA_BASE_URL` · `WAHA_API_KEY` · `WAHA_SESSION` | secrets | WhatsApp via `POST {WAHA_BASE_URL}/api/sendText` (`X-Api-Key`); session defaults to `default` |
| `WATCHDOG_ALERT_WHATSAPP` | secret | recipient digits (`<digits>@c.us`) |
| `WATCHDOG_ALERT_EMAIL` | variable | recipient; the workflow defaults it to the owner's address (owner's choice), swappable by setting the repo variable |

Missing host/key → the SSH leg is skipped with a warning; HTTP checks and alerting still run.

## 7. Install (on the VPS, as root)

```bash
cd /opt/noctus/noctusai                       # after the bless that ships deploy/watchdog/
ssh-keygen -t ed25519 -N '' -C noctus-prod-watchdog -f /root/watchdog-key   # or generate off-host
bash deploy/watchdog/install-heartbeat.sh --watchdog-pubkey /root/watchdog-key.pub
bash deploy/watchdog/install-heartbeat.sh --check --watchdog-pubkey /root/watchdog-key.pub
# put the PRIVATE key into the GitHub secret NOCTUS_VPS_WATCHDOG_KEY, then delete it from the host
```

`install-heartbeat.sh` is idempotent: copies the units into `/etc/systemd/system` only when content differs, `daemon-reload` only after a change, `systemctl enable --now noctus-heartbeat.timer`, creates `/var/lib/noctus`, and adds the key line exactly once (matched on the key body). `--check` changes nothing and also runs the probe once. Then run the workflow by hand with `send_test_alert: true` to prove each channel.

Local dry probe (sends nothing, no state): `python mcp/noctusai/cli.py --prod-watchdog` (add `--watchdog-state F`, `--send`, `--watchdog-test-alert`, `--json`).

## 8. Limits (named, so nobody trusts it for what it does not check)

- **GitHub cron is best-effort** — ticks can be delayed by many minutes or skipped under load; "every 10 min" is a target, and DOWN needs 2 runs, so detection latency is ~20 min at best and can be longer.
- **Schedules fire only from the default branch (`main`)** — the watchdog goes live at the next bless, not at merge to `dev`. Until then, run it by hand (`workflow_dispatch`) or locally.
- **WAHA runs on the VPS** — when the host is down WhatsApp is down too. That is why DOWN routes to email first; DEGRADED (host still up) prefers WhatsApp.
- **Not a metrics system** — it reads point-in-time values every 10 min; a spike between runs is invisible. Its job is "is the host alive and still keeping time", not capacity planning.
- **State lives in the Actions cache** — if the cache is evicted the watchdog starts fresh (counters reset; a still-bad state alerts again once). Each run prunes its own superseded `prod-watchdog-state-*` caches after saving; `cache-cleanup.yml` would also keep only the newest (the decimal run-id suffix matches its hex-suffix strip).
