- **2026-05-04 (Engineer C, Phase 1.4 prep):** Initial test draft used `monkeypatch.setattr(sm, "PRODUCTS_DIR", tmp_path)` to redirect path resolution. Caught mid-write — patching our own module's binding sits on the *border* of the no-monkeypatch rule (it's a config knob, not a behavioral guard, so technically defensible) but the right shape is dependency injection. Refactored to add an optional `products_dir: Path | None = None` argument to `scaffold_migration()`; tests pass it explicitly; MCP tool registration leaves it None so the seed-aware default wins. Net result: zero monkey-patching of our own module, still hermetic, simpler signature for testers, and a clean function-arg seam if other callers ever need to drive scaffolding from a non-default workspace. Lesson: when path-aware tools want hermetic tests, prefer Path-arg injection over module-binding monkey-patching even when the rule technically allows it — the `products_dir=` knob is *also* a useful affordance for the (future) "scaffold migration in template workspace" use case.

## Lessons

- **2026-05-04 (Phase 1.1):** Pre-existing email-module tests use `monkeypatch.setattr(digest_module, "_post_to_resend", ...)` which patches our own internal function name — the no-monkeypatch rule's exact anti-pattern. The module pre-dates the rule (2026-04-25). New SMTP tests patch at `smtplib.SMTP` / `SMTP_SSL` boundary directly (external-service carve-out), which is correct. Lesson: when extending a flat-shape module, tests inherit pre-rule patterns by gravity unless explicitly broken; called out in §findings instead of fixing in-scope.
- **2026-05-04 (Phase 1.3, Engineer B):** The Protocol docstring's quota math says "~2 units per page of 50 videos" for `list_channel_videos`. The actual cost on a fresh client is **3 units** (1 channels.list + 1 playlistItems.list + 1 videos.list); the "~2" assumes the caller has cached `uploads_playlist_id` from a prior `get_channel` call. Real client returns `quota_units_consumed=3` for the un-cached first call, `2` would require an in-client cache. Documented the asymmetry inline in `real.py` (`list_channel_videos`); cache enhancement is a future item. The Fake mirrors the API contract (charges 2/page) since it has no channels.list step inside `list_channel_videos` — the seed's documented `get_channel` (1) + per-page (2) is what tests assert against.

- **2026-05-04 (Engineer C, Phase 1.4):** Mirroring `scaffold.py`'s pattern revealed the *settings-import indirection* makes hermetic tests hard at first glance. `scaffold.py`'s tests work against the real repo (creating + deleting `products/test-scaffold-temp/`); for `scaffold_migration` we want fully tmp_path-based tests because the tool doesn't need a full product template — just a few stub `001_seed.sql` files. Lesson: when a sibling tool can be tested hermetically while the original couldn't, *it should be*. The `products_dir=` injection seam is a permanent affordance, not just test scaffolding — surfaces a future "scaffold migration in N=2 sibling workspaces" use case for free.

- **2026-05-04 (Engineer C, Phase 1.4):** N=2 keeper-detector-style integration tests now exist for sql_templates drift — `test_scaffold.py::TestSqlTemplatesIntegration` (created 2026-05-03) + `test_scaffold_migration.py::TestSqlTemplatesIntegration` (today). Both assert `set_search_path()` / `updated_at_function()` / `updated_at_trigger()` / `rls_subquery_policy()` outputs appear verbatim (whitespace-normalized) in the scaffolded SQL. **Recurrence rule fires at N=2** — triage time. Recommendation: extract the keeper-style integration assertion shape into a small shared helper (e.g. `mcp/noctusai/tests/_sql_templates_assertions.py` exposing `assert_sql_helper_in_body(body, helper_output)`) so the N=3 (next migration-emitting tool, or a `scaffold_migration_addsuffix` variant) consumes the helper. Filed as a follow-up *Improvement* below — not applied inline because the right destination depends on whether more SQL-emitting tools land in Phase 2/3 (the helper's home moves with the consumer count). Architect to triage at Phase 1 close.

## Knowledge pieces

- **2026-05-04:** SMTP via stdlib `smtplib` (sync) wraps cleanly with `asyncio.to_thread` to preserve the `async def send_digest(...)` signature without adding `aiosmtplib` as a dependency. Multipart/alternative is `MIMEMultipart("alternative")` + plain `MIMEText` then html `MIMEText` (order matters — most preferred renderer LAST, per RFC 2046).
- **2026-05-04:** SMTP security modes that matter: `ssl` (port 465, implicit TLS, `smtplib.SMTP_SSL`), `starttls` (port 587, explicit upgrade, `smtplib.SMTP` + `.starttls()`), `none` (port 25, plain — only useful for `aiosmtpd` test servers). Default `starttls` covers ~all modern providers.
- **2026-05-04 (Engineer A, Phase 1.2):** `cryptography.fernet.Fernet.generate_key()` returns 44 ASCII bytes (32 bytes of entropy → url-safe base64 with trailing `=` padding). The token format itself is also url-safe base64, which is why it round-trips cleanly through `.encode("ascii")` / `.decode("ascii")` and is safe to dump into TEXT columns or JSON without escaping. No length limit baked into Fernet — tested 4KB plaintext fine; the Fernet docs warn that very large payloads (multi-MB) hold the whole thing in memory, but OAuth-token sized payloads are fine.
- **2026-05-04 (Engineer A, Phase 1.2):** Wrapping `InvalidToken` in `ValueError` is the right consumer-ergonomics call: it lets product code catch decryption failures without importing `cryptography` (which would leak the choice of crypto library into call sites). Same principle the webhook_signatures module follows — return `bool` / typed dataclass, never re-raise vendor exceptions.
- **2026-05-04 (Engineer B, Phase 1.3):** YouTube Data API v3 quota costs (relevant subset):
  - `channels.list` = 1 unit (any combination of `part`).
  - `playlistItems.list` = 1 unit per page (max 50 items).
  - `videos.list` = 1 unit per call regardless of how many comma-joined ids (up to 50 in batch).
  - `search.list` = **100 units** per page (50 max items). 1% of daily quota per call.
  - Default daily quota = 10,000 units → ~100 search calls OR ~5,000 channel-video pages.
  - The auto-managed "uploads" playlist id appears on `channels.list?part=contentDetails` as `contentDetails.relatedPlaylists.uploads`.
- **2026-05-04 (Engineer B, Phase 1.3):** ISO-8601 durations from YouTube (`contentDetails.duration`) only use the H/M/S subset of the spec (no D/W/M for video durations) → simple state-machine parser is enough; no `isodate` dep needed. Fallback to 0 on parse failure with WARN log keeps a malformed entry from poisoning a whole list.
- **2026-05-04 (Engineer B, Phase 1.3):** YouTube emits `publishedAt` as RFC 3339 with a literal `Z` suffix. Python <3.11 chokes on `Z`; replace with `+00:00` before `datetime.fromisoformat`. Tested on Python 3.11 (works either way) but the replace stays for portability.

- **2026-05-04 (Engineer E, Phase 2.3):** When generalizing the Google OAuth flow into a Protocol+concrete pattern, the calendar-side `oauth_adapter.py` and the media-scheduling `oauth.py` router took two visibly different approaches to the same dance — calendar uses the `google.oauth2.credentials.Credentials` SDK to handle refresh transparently inside `_service()`, while media-scheduling raw-POSTs to `https://oauth2.googleapis.com/token`. The new `GoogleProvider` adopts the raw-POST path because that's the only one that gives us a clean four-method Protocol surface (the SDK approach is async-unfriendly and couples credential storage to refresh). Sibling parity test (`test_google_token_url_matches_calendar_adapter_default`) asserts the new module hits the same URL as `OAuthCalendarCredentials.token_uri` so a future migration is shape-neutral. Lesson: when lifting cross-product code, prefer the path that maps cleanly to the new Protocol over the path that "looks more like the SDK" — SDKs hide complexity that becomes a leakage point at the Protocol boundary.

- **2026-05-04 (Engineer E, Phase 2.3):** Hook-failure semantics in `oauth_router` deserved an explicit decision. Three options: (a) bubble hook exception as 500, (b) swallow silently and log, (c) surface in `result.error` so the consumer sees it in the JSON. Picked (c) per "no silent errors" — a hook failure (e.g. DB write down) is consumer-actionable and should land visibly without crashing the OAuth flow. Tested explicitly. Lesson: `on_callback` hooks straddle library/consumer boundary; hook failures are first-class results, not internal errors.

- **2026-05-04 (Engineer E, Phase 2.3):** `httpx.AsyncClient` mocked at the class boundary (`patch("httpx.AsyncClient", return_value=mock_client)`) is the right shape — it's an external dependency per the testing rule's external-service carve-out. The Provider's own `_post` helper is exercised directly. Avoided the temptation to test `_post` separately; testing through the public method `exchange_code(...)` keeps the test surface aligned with the Protocol contract instead of internal implementation details.
