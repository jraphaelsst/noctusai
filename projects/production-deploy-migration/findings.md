## Lessons

- **2026-05-21 — Verify infra against the live DNS, never against the stated stack or the KB.** The user believed Hostinger+Coolify; the KB said the VPS hosts the app with Let's Encrypt; reality (TXT + headers) said Replit-on-GCP. `dig`/`curl -I` settled it in seconds. (Codebase-is-source-of-truth applies to infra too.)
- **2026-05-21 — Named tunnel ≠ quick tunnel.** The user remembered tunnels as a throwaway dev thing — that's the *quick* tunnel. The *named* tunnel is the persistent, production-sanctioned mode. The distinction is the whole answer to "why is tunnel a real deploy solution." (See PROJECT §2 / response 2026-05-21.)
- **2026-05-21 — "Move DNS to CF" ≠ "transfer the domain to CF".** Two separate operations: a **nameserver change** (delegates the DNS-host role; fast, free, reversible — and ALL the cutover needs) vs a **registrar transfer** (moves ownership/billing; ~5 days, optional). Never block the deploy on the slow one.
- **2026-05-21 — The management UI is not the registrar.** Domain "lived in Replit" but the registrar of record is name.com. Always `whois` to find the true registrar before planning unlock/transfer/NS work.
- **2026-05-21 — "Migrate ALL to Cloudflare" has a hard ceiling — and the honest answer evolves with CF's product line.** Don't answer "can CF host this?" from memory; check current capabilities (CF Containers went GA / grew 15× since early 2026). The durable distinction: **edge = yes, fully CF; compute = needs a server, or a rewrite onto CF's serverless model.** Honor the user's *intent* (fewer vendors) by maxing the CF edge + collapsing to ONE compute box, not by pretending CF replaces a VPS for a docker-compose fleet.

## Lessons (swap)

- **`docker compose` interpolates `${VAR:?}` on EVERY subcommand, not just `up`.** `compose ps`/`exec` without `--env-file .env.services` aborted with "required variable … missing" though services were up. Pass `--env-file` to every compose invocation.
- **`depends_on` pulls in services you didn't name in `up`.** `compose up -d postgres n8n waha` also started `redis` (depends_on) → an alias-`redis` collision with the fleet's noctus-redis. n8n/waha don't need redis (SQLite + sessions-volume) → dropped the redis service + depends_on. Two containers sharing a network alias = ambiguous DNS.
- **cloudflared runs as nonroot (uid 65532)** → a root-owned 0600 creds file is unreadable (perm-denied loop). chown creds to 65532, keep 0600.
- **WAHA persists auth but does NOT auto-start saved sessions** → after a swap, `GET /api/sessions` = `[]`; `POST /api/sessions/<name>/start` resumes from the volume with no re-pair.
- **Don't add a hostname to Caddy/LE BEFORE its A-record exists — a failed ACME attempt poisons Let's Encrypt's DNS negative-cache.** Phase 2 brought Caddy up with core/erp/social in the Caddyfile before their A-records → LE cached `NXDOMAIN` (TTL = the zone SOA negative-TTL, here **3600s**). Even after the records were added, LE kept returning the cached NXDOMAIN. **Right sequence:** A-record first → THEN add the host to Caddy. **Recovery (no 1h wait needed if it clears early):** poll public resolvers (`dig @1.1.1.1 / @8.8.8.8 / @9.9.9.9`) — once they return the record, `docker restart noctus-caddy` to clear Caddy's ACME backoff → certs issue first try. Here the cache cleared in ~15min, not the full hour.
- **A local resolver's negative-cache is independent of the world.** The agent's own machine kept returning NXDOMAIN for core/erp long after public resolvers + LE had the records → verify external reachability with `curl --resolve <host>:443:<ip>` (bypasses the local stale cache), not the bare hostname.
- **Legacy build — platform-auto-installed deps missing from the manifest (N=2, generalized → KB GUIDE §6).** Replit's packager installed deps WITHOUT writing them to the committed manifest, so a clean `docker build` missed them — twice in the `one-permutas` build: ① **npm root-hoist** — `@supabase/supabase-js` was in the ROOT `package.json` (resolved via hoisted parent `node_modules`), invisible to an isolated `frontend/` `npm ci` → `TS2307` → fix `npm ci && npm install --no-save @supabase/supabase-js@^2.90.1`; ② **pip framework-implicit** — `Pillow` (Django `ImageField`) wasn't in `requirements.txt` at all → `fields.E210` at `manage.py` system check → fix `pip install -r requirements.txt "Pillow>=10.0"`. App-source import scan (excluding the committed `venv/`) confirmed those were the only gaps. **Detect fast:** run the FE `build` + `collectstatic`/`check` in the Dockerfile so missing deps fail the build, not prod. Plus a Django shim-path gotcha: the prod-settings shim must live in the **config package** `backend/backend/` (next to `settings.py`), not the project root, for `DJANGO_SETTINGS_MODULE=backend.settings_prod` to import (`ModuleNotFoundError` bit the first attempt).
