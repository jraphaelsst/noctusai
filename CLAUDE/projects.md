# CLAUDE/projects.md — project-execution behavioral rules

> **Loading discipline.** This file is not auto-loaded. Read it when scaffolding / executing / closing a project, when handling a phase, or when handling a `*-PROJECT.md` file. The §3 routing table in `CLAUDE.md` is the canonical signal. Sibling of `CLAUDE.md`, NOT depth (depth lives in `KNOWLEDGE-BASE/`).

## Rules

- **Phase 0 audits — highest-leverage; expand loudly on invalidation.** Every project's first phase reads the actual files / runs the actual commands / queries the actual DB before any code lands. When findings invalidate §6, **revise §6 in-place + log in §11 + continue.** Do NOT silently absorb; do NOT halt indefinitely. STOP is required only for hard-to-reverse + multi-agent-shared actions, security/LGPD design-class discoveries, or scope changes the user explicitly asked to confirm. Phase 0 takes 5-30 min; mis-scopes it prevents take 2-8 hr. → `KB § PATTERNS/project-execution.md § 2.5 Phase 0 audits`
- **The execution workflow — top-to-bottom rigor, every project.** Canonical loop: SCAFFOLD (§3a seed-first) → PRE-PHASE (§2.5 audit + `noctus.hound.scan`) → EXECUTE one phase (§2.6 active robustness review, §2 live ticking, mid-phase scan checkpoints, §6↔§11 self-check) → PHASE-END VERIFICATION (tests + keeper + `noctus.hound.scan` rerun + KB sync + §6↔§11) → CLOSE-PHASE (synthesize improvements → ONE bundled proposal → apply-inline-then-delete → commit the phase locally, no push) → PROJECT-END VERIFICATION (cross-product builds + backend tests + MCP tests + full keeper + sync verifiers + final `noctus.hound.scan` + three-way sync + end-of-work summary) → PROJECT CLOSE (folder deletion → final commit + push as the literal last step). **Code-quality bias**: when picking between quick and thorough, pick thorough. → `KB § PATTERNS/project-execution.md § 0 The execution workflow`
- **Commit per phase, branch-push at project close, orchestrator FF-to-main as the literal last step — the only auto-commit/push gates.** Three carve-outs amend the never-auto-commit rule: (1) end of every phase, stage the phase's diff with explicit file paths and create a phase-scoped local commit (no push); (2) at project close (after folder ARCHIVE via `noctus.dev.archive` — see archive-on-close bullet below), stage anything still uncommitted and `git push` to the BRANCH; (3) **orchestrator FF-push to main — the literal last step of project close, NON-NEGOTIABLE GATE (NEW 2026-05-10).** Branch-pushed ≠ main-merged; without the FF, branches accumulate post-close on the remote (10+ unmerged branches observed 2026-05-10 — slip recorded in KB §11). The FF push runs AFTER the orchestrator's fresh-eyes review: `git diff origin/main..origin/<branch>` (review) → `git push origin origin/<branch>:main` (FF). **Project is NOT closed until main reflects the work.** Same-agent carve-out preserved (per `feedback_orchestrator_role.md` — mode-switch + re-read diff when no subagent was spawned). When FF fails (branch is behind main), the merging methodology applies (`KB § PATTERNS/branching-and-merging.md §10`) — rebase or merge origin/main into branch first, resolve conflicts via file-type heuristics (§10.4), then FF. The "explicit-delegation" carve-out: when the user gives a project-close instruction like "commit and push the project" or "c-push", all three gates run without re-confirmation. Always `git status` first; never `git add .` / `-A`. → `KB § PATTERNS/project-execution.md § 0 The execution workflow`
- **Commit + push only your own work — authorship discipline.** Each agent commits and pushes ONLY files they authored or modified in the current session. Parallel-agent work in the working tree (modified or untracked files you didn't touch) belongs to whoever's authoring it — not yours. Explicit-path `git add` does NOT validate authorship; staging a directory or untracked path can sweep up parallel-agent work. **Protocol every commit + push:** (1) enumerate YOUR files mentally before staging; (2) stage by individual file, never by directory if a parallel agent might have added files there; (3) `git diff --cached --name-only` — every entry should match your mental list, surprises → unstage and investigate; (4) before push, `git log origin/<branch>..HEAD --format='%h %an %s'` — any commit you didn't author → STOP and ask. Drive-by exception: minimal non-destructive fix to unblock a hook on a parallel-agent file (per § 2.9 resolution-path-2), documented in commit message. **The 2026-05-03 violation that drove this rule:** Vista formalize commit `9b94f60` swept up an entire parallel-agent file + a parallel KB modification because authorship was not verified. → `KB § PATTERNS/project-execution.md § 2.10`
- **Branch when parallel-agent commits sit in your unpushed range — branching is the structural solution to authorship-violation pressure.** If `git log origin/main..HEAD` shows commits you did not author, do NOT push from local main. Instead: `git checkout -b <branch> origin/main` (branch from REMOTE main, not local), cherry-pick your commits onto the branch, push the branch. Two push shapes: (a) **branch-to-branch** `git push -u origin <branch>` for in-flight / review work; (b) **branch-tip-to-main fast-forward** `git push origin <branch>:main` when ready to ship and `origin/main` is still ancestral to your branch tip (no other commits landed in between). Never `--force` to main. Naming: `<project-slug>-shipped` for ready-to-ship; `<project-slug>-wip` for in-flight; `<topic>` for cross-cutting. Mental model + anti-patterns + the cherry-pick recipe in KB. **When fast-forward push fails (non-FF), the merging methodology applies** — rebase OR merge origin/main into branch (KB §10.2); same-line conflicts use file-type heuristics (KB §10.4 — concat for KB docs / alphabetical for MCP registrations / NEVER-conflict for migrations / union for tests / read-base for production code); recovery from bad merges via reflog + ORIG_HEAD or `git revert -m 1 <merge-commit>` for already-pushed mistakes (KB §10.6 — never `--force` push to fix). → `KB § PATTERNS/branching-and-merging.md`
- **Worktree-base verification — every engineer brief carries the preamble.** When dispatching engineers via the `Agent` tool with `isolation: "worktree"`, the harness creates the worktree from `main`, NOT from the orchestrator's branch tip. Engineers' worktrees may be missing in-flight commits — silently editing on a stale base regresses the orchestrator's work at merge time. **The architect-side fix:** every engineer brief MUST start with the §16.7 preamble — orchestrator-branch + orchestrator-tip-sha + reset directive + STOP-and-report fallback. **Push the branch BEFORE dispatching** when 2+ engineers will run in parallel, so the recovery path becomes mechanical (`git fetch origin <branch> && git reset --hard origin/<branch>`). Companion to the §17.6 Write-authorization clause — both live at the top of the brief, before task-specific content. Confirmed gap from AdConnect MVP 2026-05-10 (6+ engineer self-recoveries; one stale-base regression caught at merge). → `KB § PATTERNS/branching-and-merging.md § 16.7`
- **Branch-per-project workflow + orchestrator-merges.** Phase commits go to the project's (or feature's) branch, NOT main. Final commit + push at deliverable lands on the branch (branch-to-branch). The **orchestrator** (CLI agent in the user's session-spanning conversation) does the final merge to main — fresh-eyes pass before fast-forward push. Working agents (subagents spawned via Task, or the CLI agent in implementer-mode) commit and push to the branch but never to main. **Why the split is structural, not capability-driven**: implementation rationalizes its own design; merge-time review from a different vantage point catches integration concerns the implementer rationalized away. The methodology survives any model-behavior shift because it depends on **structural separation** (different contexts, different vantage points), not on Claude-specific tendencies. When same agent acts as both: mode-switching (separate turn between implementation and review) preserves the mechanism. **Master-tree adaptation (§11.1)**: master-tree branch from origin/main; each child branches from the master-tree branch (NOT origin/main); children land back on master; master eventually lands on origin/main. Hierarchical branching mirrors the hierarchical project structure. → `KB § PATTERNS/branching-and-merging.md § 11-12`
- **Branch-creation triggers project/feature filing — branch first, file second, implement third.** Trigger phrases: `"branch this"`, `"branch X"`, `"create another branch for Y"` (2 words minimum, longer phrases also count). Sequence: (1) `git checkout -b <slug> origin/main` — slug = the project/feature name; one source of truth. (2) File `templates/PROJECT-TEMPLATE.md` for projects OR `<slug>.md` for features. (3) Then implement. Branch-first prevents the "started editing on main, then realized I should have branched" slip. → `KB § PATTERNS/branching-and-merging.md § 13`
- **Pre-work fetch protocol — collision avoidance, not collision recovery.** Before any agent starts substantive work on a scope: `git fetch origin` + `git branch -a` + `git log --all -- <files-of-interest>`. If a parallel agent is already working overlapping scope: do NOT start your colliding edits yet. Work on next steps that don't overlap; wait for the parallel agent to commit; merge their work into your branch; then attack the previously-colliding scope (recurse if next steps also collide). Cost: ~5s per startup. Benefit: collisions caught BEFORE editing. Companion to `§ 2.9 Parallel-agent collision protocol` (proactive vs after-the-fact). → `KB § PATTERNS/branching-and-merging.md § 14`
- **Features — durable callable utilities (concept refined 2026-05-03).** Single `.md` file (no folder, no §1-§12 ceremony, no §3a seed-first analysis required). **Features are tools / utilities / patterns / methodology entries that get called or referenced later — NOT throwaway temporary files.** Locations mirror projects: `features/<slug>.md` (cross-cutting), `products/<x>/features/<slug>.md`, `core/features/<slug>.md`. Discriminator: ≤2 sub-tasks AND ≤1-2 files AND no multi-phase plan → feature; otherwise → project. Promotion path: a feature that grows beyond scope gets promoted to a project folder. Get the same branch-per-project + branch-creation-triggers + orchestrator-merges treatment as projects. **On close: feature .md STAYS at its location** (NOT auto-archived — features are durable callable utilities, not deliverables). Only explicit user "delete X" / "remove X" → `git rm` (deletion is the override; default = stays in place). Trivial direct fixes (typo, broken link) skip both filing and branching. → `KB § PATTERNS/project-execution.md § 11.1 Features`
- **Archive-on-close — closed PROJECTS move to `archive/`, not deleted. (Features are durable; they don't archive.)** Project close gate: `noctus.dev.archive` moves `projects/<slug>/` to `archive/projects/<today>/<NN>-<slug>/` via `git mv` (preserves history). User says "archive X" → same tool, mode by category or explicit `ad_hoc` for ad-hoc artifacts (lands at `archive/<YYYY-MM-DD>_<HH-MM-SS>_<name>/`). Features can be explicitly archived via `noctus.dev.archive(mode="feature")` if user asks, but NOT auto-archived on close (per features bullet above). **User says "delete X" / "remove X" → `git rm -r` (explicit-override; archive is the auto-default for projects).** Idempotency guard: refuses if target already lives under `archive/`. Stash drops, memory deletes are deletes (not deliverables). → `KB § PATTERNS/project-execution.md § 11.2 Archive system`
- **Exploratory branching — branch-and-compare and merge-upfront.** Two patterns triggered by user phrasing, not detection. **Branch-and-compare** ("branch 2 things and compare", "A vs B", "let's try both", "spike", "experiment"): each approach gets its own branch from origin/main; both ship in isolation; orchestrator presents comparison (diff size, tests, methodology fit, readability, perf, UX); user picks winner; loser branch gets `-abandoned` suffix. **Merge-upfront** ("merge them upfront", "hybrid", "combine", "union"): both approaches on a single branch as the union; compared against origin/main baseline; shipped if union holds. Default when phrasing ambiguous: **ask** ("compare or combine?"). → `KB § PATTERNS/branching-and-merging.md § 15`
- **§6 ↔ §11 consistency self-check before claiming a phase is done.** Verify all five: (1) §6 header carries `✅`, (2) every sub-task `- [x]`, (3) `**Improvements:**` block filled (or `none identified.`), (4) §11 entry exists, (5) `improvements.md` regenerated. If any is missing, the phase is NOT closed. Live state never lags the narrative. → `KB § PATTERNS/project-execution.md § 2 Self-check before claiming a phase is done`
- **Active robustness review during execution.** Phase execution is *also* a proactive inspection pass on the code you touch + its surroundings. Eyes open: silent error swallows (`except: pass`), stale TODOs, untyped `any`/`unknown`, async races, hardcoded magic numbers, missing trust-boundary validation, fields populated-and-never-read, mock-vs-real divergence. Capture findings live in the phase's `**Improvements:**` block — in-the-act, NOT saved for later. Apply low-risk inline, scope-creep refactors are forbidden. *Empty improvements after a non-trivial multi-file phase ≈ inspection skipped.* → `KB § PATTERNS/project-execution.md § 2.6 Active robustness review`
- **Phase enrichment loop — every shipped phase enriches the next phase with new learnings.** When a phase ships, log ≥1 non-obvious learning via `noctus.dev.phase_learning_log` (kinds: `methodology` / `technical` / `process` / `tool` / `other`). Before opening the next phase, query unconsumed learnings via `noctus.dev.phase_learning_query` with `unconsumed_only=True`, fold relevant ones into the next phase's plan, mark consumed via `noctus.dev.phase_learning_consume`. Local SQLite at `mcp/noctusai/data/phase_learnings.db` (gitignored). Methodology-level learnings get three-way-synced (KB + topical + memory); cross-cutting patterns get promoted to the absorption catalog. → `KB § PATTERNS/project-execution.md § 2.11 Phase enrichment loop`
- **Projects live next to the code they touch — three valid locations, scope-scoped.** `projects/<slug>/` for **cross-product / seed / platform-infra / not-yet-a-product**; `products/<product>/projects/<slug>/` for **single-product scope**; `core/projects/<slug>/` for **core-platform-control-plane** (auth, SSO, billing, orgs, entitlements). Slugs globally unique. Each folder holds `PROJECT.md` + `improvements.md` + `proposals/`. **Always start by copying `templates/PROJECT-TEMPLATE.md`.** Slug convention: `<subject>-<intent>`. **Interrogate the user before drafting.** **Write for a zero-context reader.** **Live-tick `- [ ]` → `- [x]` immediately.** **Cadence is phase-by-phase by default** — pause and wait for "continue" between phases unless the user asks for throughput. **Phase headers carry status icons** (no icon = pending, `⏳` = partial, `✅` = complete, `❌` = blocked). **Improvement flow is capture-then-synthesize**: drop in-the-act bullets in `**Improvements:**` during the phase, then at end-of-phase BEFORE flipping `✅`, file ONE bundled proposal via `noctus.dev.file_proposal(project="<slug>", ...)` with `Origin: project:<slug>:phase-<N>`. Then flip header, run `python mcp/noctusai/cli.py --improvements <PROJECT.md path>`. → `KB § 01-PHILOSOPHY.md § Projects are living` + `KB § PATTERNS/project-execution.md §1` + `KB § PATTERNS/proposals-and-improvements.md`
- **Auto-improvement at phase close — apply, don't ask.** At end of phase, read the `**Improvements:**` block and **apply every in-scope, low-risk, self-contained item INLINE in the same session — no `noctus.dev.file_proposal` artifact, no user prompt**. Mark each item as `applied` or `deferred → <destination>` in the block; that block + §11 ARE the audit trail. **Defer** items that are out-of-scope or need their own project (scaffold the follow-up from `templates/PROJECT-TEMPLATE.md` — broken pointers forbidden). **Still file a formal proposal** when items need scheduling, explicit human approval (security/public-API), or batch-review across deliverables. End every non-trivial reply with a list-shaped summary (applied / deferred / verification). → `KB § PATTERNS/proposals-and-improvements.md § 4d + § 4c`
- **In-flight resolution — clear-path deferrals/accept resolve in the SAME commit, not later.** A deferral *or* accept-with-rationale whose **resolution path is clear/recommended ∧ resolvable-now within scope** is resolved **in-flight** and lands in the **same commit as the deliverable** (commit-on-ship). Parking/deferring is the exception — strictly genuinely-unclear ∨ out-of-scope ∨ needs-a-decision ∨ hard-to-reverse — and that exception is announced loudly. Discriminator: *"clear/recommended ∧ resolvable now in-scope?"* yes ⇒ do-it-now-same-commit; no ⇒ defer-with-destination ∨ accept, announced. A clear recommended fix is work-to-do-now, ¬ a triage outcome to file. Unifies defer≠resolve (R5) + commit-on-ship (§21.4) + accept-with-rationale. → `KB § PATTERNS/project-execution.md § 2.13`
- **No-defer-mid-flight (2026-05-20 refinement of §2.13).** The exception list NARROWS. ONLY two sanctioned reasons to file a follow-up project / stub PROJECT.md: (a) **external structural blocker** — vendor API quota / read-only-v1 SDK / hardware-locked dep / multi-week security project — *must be named and external*, never "we haven't decided" or "out-of-scope for this project"; (b) **hard-to-reverse work needing explicit user gating** — destructive migration / billing impact / public API contract break. Everything else (including *"pending interrogation"*, *"needs a decision"*, *"phase N follow-up"*, *"lift to seed when N=2 if buildable now"*) implements **inline, same commit, same session**. Auto-mode contract: agent IS the decider — make the reasonable provisional call, surface as a §11 Change Log entry the user can flip. The reflex *"I'll file a separate project for this"* during close-out IS the slip signature — when reaching for PROJECT-TEMPLATE in the middle of close, stop and ask *"why not now?"* (answer: almost always no real reason). Bit 2026-05-20: media-creator-w2-4 close-out almost filed `image-gen-seed-adapter` as a pending-interrogation stub; user intervened, the full Protocol+Fake+Real(Gemini)+factory adapter shipped inline in ~30 min vs the ~3-week follow-up overhead. → `KB § PATTERNS/project-execution.md § 2.13a`
- **Every product has `README.md` + `MASTER-PROMPT.md`.** README for humans browsing the repo; MASTER-PROMPT for agents building features. Both mandatory from day one. → `KB § GUIDES/new-product.md`
