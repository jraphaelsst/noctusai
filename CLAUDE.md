## 1 · Engineering Philosophy

Behavioral rules. Short on purpose. For the long-form reasoning — history, incidents that produced the rule, edge cases — read **`KNOWLEDGE-BASE/CONTEXT/01-PHILOSOPHY.md`**.

> **Vocabulary note (per user 2026-04-27):** these are our **methodology** — not a "doctrine". Use *methodology / rule / principle / convention / pattern / working agreement* in writing. Avoid "doctrine / doctrinal / doctrinally" — the framing is hierarchical and runs counter to how this team actually operates. → `KNOWLEDGE-BASE/CONTEXT/01-PHILOSOPHY.md § Vocabulary — methodology, not doctrine`

- **Seed is the skeleton. First rule.** `seed/` owns the structural bones of the platform; products are organs that attach to that skeleton through **runtime import**, not copy-paste. Backend calls `create_product_app()` from `noctusai_seed`; frontend calls `createProductApp()` from `@noctusai/seed`. The authoritative methodology — the skeleton analogy, what must live in seed, what products may own, every named extension seam, and every out-of-contract pattern — lives at `KNOWLEDGE-BASE/CONTEXT/03-SEED-ARCHITECTURE.md § Seed as Skeleton` + `§ Seed Contract`. Any product customization flows through a NAMED seam (`standard_routers=[...]`, `authProvider`, `Layout`, `lifespan_*`, etc.); a customization NOT flowing through a named seam is a **structural fork** and either (a) gets refactored to use an existing seam, (b) triggers an existing seam to be extended, or (c) triggers a new seam to be formalized in `KB § 03-SEED-ARCHITECTURE.md § Seed Contract`. The two supported auth paths (Supabase-based for consumer products, `authProvider` for identity-source products like core) are documented in `§ Control-plane vs. consumer products`. Identity-source products compose `noctusai_lib.auth.create_sso_token_factory(settings)` + `verify_sso_token_factory(settings)` + `SSOSessionCache(ttl_seconds)` from the seed lib; endpoint routers (`/api/auth/*`, `/api/sso/*`, `/api/oauth/*`) stay as organ routers in the product (promote to framework bundle when a 2nd identity-source product surfaces — recurrence rule). Full seam shape at `§ Seed Contract § 3 Control-plane product seam`. **Don't ask whether to use the seed. Don't propose alternatives. The seed IS the approach.** Before any structural change, run the **4-question Practical Decision Test** (`KB § 03-SEED-ARCHITECTURE.md § Practical decision test`): bone or organ? if bone, why not in seed? if organ, is it just duplicated structure in domain clothes? will changing seed propagate? A "no" on the last question means the inheritance chain is broken — fix that first. As of 2026-04-22 every product is seed-compliant on both backend and frontend per the § Compliance check audit. Fix structural issues in the seed, never in individual products. *If a structural fix requires editing multiple products manually, the skeleton model is drifting.* **Remediation for a non-compliant product is a focused project**: slug `<product>-seed-wiring`, location `products/<product>/projects/<product>-seed-wiring/`, scope = rewrite `main.py` / `main.tsx` / `App.tsx` around the seed factories and preserve the test baseline. Non-compliance is never grandfathered — either a `<product>-seed-wiring` project is filed, or the divergence is accept-with-rationale per § Seed Contract § 4 triage. → `KNOWLEDGE-BASE/CONTEXT/03-SEED-ARCHITECTURE.md § Seed as Skeleton` + `§ Practical decision test` + `§ Seed Contract` + `KNOWLEDGE-BASE/CONTEXT/01-PHILOSOPHY.md § Seed first — Always § Compliance`
- **MCP toolkit reviews after every change (observation-only).** After modifying code, run `python mcp/noctusai/cli.py --review` on the affected product. The review pass detects seed-compliance issues deterministically and asks an LLM (OpenAI, via `OPENAI_API_KEY`) to author a proposal for each. Keeper-originated proposals land in `products/<product>/proposals/` (scoped to the product the detector flagged); **project-scoped proposals land in the project's own `proposals/` folder** — `projects/<slug>/proposals/` for cross-product/platform work, `products/<product>/projects/<slug>/proposals/` for product-scoped work (the MCP tool resolves from the slug). See the "Projects are living" rule below. **The tool NEVER modifies code** — every decision goes through explicit human review. *No code ships with unreviewed violations.* Loop: change → review → triage proposals → apply manually → commit. The old auto-fix `--heal` flow was retired because deterministic text rewrites could corrupt code and the string-match checks rotted as the seed evolved. → `KNOWLEDGE-BASE/CONTEXT/06-AGENTS.md`
- **No incomplete commits.** Never commit a product with mismatched maturity between backend and frontend. "Scaffolded" is not "complete." If one side is real and the other is a placeholder, stop and flag it. *A commit that looks done but isn't becomes tech debt the moment it lands.*
- **No quick fixes.** Never patch symptoms. If a fix touches multiple products for the same reason, you're fixing the wrong level. Go one layer up — the real fix lives in the seed, a shared lib, or a config — and it propagates automatically. *Thirty minutes on the root beats five minutes on a patch that generates future work.*
- **No workarounds — and no monkey-patching, in production OR tests.** Use the real API, SDK, or framework. No monkeypatches, shims, or hacks. *If the framework can't do it, extend the framework — don't bolt onto the product.* **The rule applies to test code too.** Never `monkeypatch.setattr(our_module, "our_guard", _noop)` (or `patch.object(our_module, "our_guard", ...)`) to make a test pass — that test is no longer exercising the guard. The right test seeds the data the real guard reads (e.g. `ai_consent` rows for `noctusai_lib.ai.consent.require`) and uses dependency injection for write side-effects (an optional kwarg defaulting to the real client, with tests passing a mock). When verifying inserts, read `MockRequestBuilder.inserted_payloads` from the seed-lib mock — don't patch the helper that wrote them. `unittest.mock.patch.object(<external_integration>, ...)` for **external services** (LLM APIs, transcription, network calls) remains the right tool — that's mocking the boundary, not neutering our own code. → `KNOWLEDGE-BASE/CONTEXT/PATTERNS/testing.md § Consent-guard product conftest pattern § Service-layer guards` + `KNOWLEDGE-BASE/CONTEXT/01-PHILOSOPHY.md § No workarounds`
- **Estimate off evidence, not structure.** Before offering scope options (A/B/C), a session-size, or "this is quick" — **open the files the change would actually touch**. If it would affect `seed/`, a shared lib, a factory, or any cross-cutting layer, read that code first. Shallow estimates force mid-flight course-corrections that waste tokens and erode trust. If you already offered a shallow estimate and then discover the real scope, stop and re-scope as a proper project — don't silently continue. → `KNOWLEDGE-BASE/CONTEXT/01-PHILOSOPHY.md` (Estimate off evidence)
- **DRY.** Three similar blocks is a pattern — extract it. Two is a coincidence. Single authoritative source for every piece of logic, every config, every doc.
- **Componentize everything.** Before writing anything, check **`KNOWLEDGE-BASE/CONTEXT/04-SHARED-LIBRARY.md`** — it might already exist. If another product will need it, build it shared from the start. *Duplicate code is debt; shared components are assets.*
- **Replication-to-seed symmetry — fires at READ/PLAN/DESCRIBE time, not just edit time.** *The trigger is LANGUAGE, not action.* The moment you see or write any of these phrasings — in your own response, in a project doc someone else wrote, in a user prompt, anywhere — STOP and challenge: **"per-product X"**, **"mount across N products"**, **"for each product Y"**, **"per-product mount table"**, **"mount on each ___"**, **"every product gets its own ___"**. Those phrasings ARE the slip. The design they describe is wrong, even if it's the design enshrined in an existing PROJECT.md. Components, mounts, routes, settings pages, dashboard widgets, scaffold lines, conftest setup — if every product needs the identical thing, it lives ONCE in seed (`seed/frontend/lib/`, `seed/frontend/framework/createProductApp(...)`, `seed/backend/framework/create_product_app(...)`, `noctusai_lib.*`, `noctusai_seed.*`). The right per-product code count for a cross-product concern is **zero** — products opt in via a kwarg or it auto-on by convention; they don't reimplement, mount, or wire anything by hand. **Recurring slip pattern (caught 4× in 2026-04-27 → 2026-04-28: vitest config replication, monkeypatch as documented "variant" pattern, conftest test-bootstrap line replication, consent-ui-rollout mount-per-product framing).** The 4th caught happened inside the same reply that documented the first 3 — proof the rule has to fire at *language* time to stick. Companion rules: retroactive `Audit seed completeness proactively`; at-edit-time check before edit #2 (the language check fires earlier — at read/plan/describe time, before any edit happens). When reading an existing PROJECT.md that uses replication framing, the FIRST move is to challenge the framing in Phase 0 — don't parrot it. **Authoring-time corrective: EVERY `PROJECT.md` MUST include §3a Seed-first analysis (six-question checklist + per-product code-count litmus) BEFORE §6 phase planning** — see `templates/PROJECT-TEMPLATE.md` § 3a + `KB § GUIDES/seed-first-design.md`. *Every* project, not just cross-product — the seed is every product's skeleton, so single-product projects also might have patterns/components/helpers better placed in seed. Single-product projects whose answers all point at product-specific still fill §3a (the explicit confirmation that the design is correctly product-bounded). Future agents deliver projects already seed-thought; the user does not refactor projects to apply seed-first thinking after the fact. A `PROJECT.md` lacking §3a is a bug. → `KNOWLEDGE-BASE/CONTEXT/PATTERNS/project-execution.md § Self-check before the second per-product edit` + `KNOWLEDGE-BASE/CONTEXT/GUIDES/seed-first-design.md`
- **Module-scope imports.** Python imports go at the top of the file. Don't defer imports into function bodies unless solving a documented circular dependency. *Top-level imports fail fast at startup; deferred imports hide bugs until a specific path runs.*
- **FastAPI dep factories defer config to request time.** When designing a seed-lib helper that products mount via `Depends(...)` (router-level guards / preconditions), the factory MUST be lenient at call time and check configuration inside the returned dep at request time. Routers decorate at import-time but `create_product_app(...)` wires `configure_X_module(...)` later — a fail-fast factory crashes router imports. Pattern: module-level `_X` slots default `None`, `configure_X_module(...)` populates them, factory returns dep without checking; dep reads slots at request time. Ship a `bind_X_module_to_mock(mock_sb)` helper in `noctusai_lib.testing` for product conftests (TestClient caches the app, so per-fixture rewire is required). Reference adopters: `noctusai_lib.ai.consent.consent_required` + `noctusai_lib.llm.budget.configure_budget_module`. → `KNOWLEDGE-BASE/CONTEXT/PATTERNS/backend.md § FastAPI dependency factories with module-level injection`
- **Phase 0 audits are the highest-leverage work in any project — and when findings invalidate §6, *expand loudly* (don't stop).** Every project's first phase is an audit — read the actual files, run the actual commands, query the actual DB — before any code lands. Phase 0 frequently surfaces that the project itself is mis-scoped (too small, too large, or wrong direction). **When findings invalidate §6, REVISE the §6 plan to match reality in the same session** + log the divergence in §11 + continue execution. Do NOT silently absorb the discovery (hides drift); do NOT halt indefinitely waiting for re-approval (gates progress on small re-scoping moments). The "expand loudly" rule means: surface every change explicitly, keep the document the source of truth, and keep moving. **STOP is still required** for hard-to-reverse + multi-agent-shared actions (force pushes, branch deletions, prod migrations, public API breaks), security/LGPD design-class discoveries, or when the user explicitly asked to confirm scope changes — those classes warrant explicit confirmation. For everything else (small re-scopes, new tasks, dropped tasks, expanded plans), expand loudly + continue. Worked examples: `frontend-test-harness` Phase 0 caught ERP's vitest was actually red for 9 of 10 files; `pf-schema-drift-reconciliation` Phase 0 caught a structural ~13-table divergence. `repo-state-consolidation` Phase 0 (2026-04-28) is the inaugural use of expand-loudly — found working-tree drift from 430 → 470 entries, revised commit plan in-place. Phase 0 takes 5-30 min; mis-scope discoveries it prevents take 2-8hr. Don't skip it. → `KNOWLEDGE-BASE/CONTEXT/PATTERNS/project-execution.md § 2.5 Phase 0 audits`
- **The execution workflow — top-to-bottom rigor, every project.** Every project follows the same canonical loop: SCAFFOLD (§3a seed-first checklist) → EXECUTE one phase at a time (§2.5 Phase 0 audit, §2.6 active robustness review, §2 live ticking, §6↔§11 self-check at phase close) → CLOSE-PHASE (synthesize improvements, file ONE bundled proposal, apply-inline-then-delete) → PROJECT CLOSE (three-way doc sync, verify KB + keeper + builds + tests, delete folder, end-of-work summary). Cross-cutting language trigger fires at every step. No monkey-patching, no silent errors, no replication framing, three-way doc sync. **The discipline at each step is non-negotiable.** The full workflow lives at one anchor — `KNOWLEDGE-BASE/CONTEXT/PATTERNS/project-execution.md § 0 The execution workflow` — which indexes every named rule that fires inside it. Future agents operate this loop end-to-end. → `KNOWLEDGE-BASE/CONTEXT/PATTERNS/project-execution.md § 0 The execution workflow`
- **The recurrence rule — formalize patterns at threshold, not "later".** When you observe the same pattern / boilerplate / code shape in N independent places (during Phase 0 audit, active robustness review, KB pass, cross-product spot-checks): **N=2 → triage time** (formalize / refactor / accept-with-rationale, decision recorded — silently moving on is forbidden); **N=3+ → MUST formalize** (extract into seed-lib / seed-framework / shared library; minimum acceptable response is filing a follow-up project from `templates/PROJECT-TEMPLATE.md`; silently shipping the 4th instance is forbidden). When the rule fires, STOP, name the pattern, decide the destination (`seed/backend/lib/`, `seed/frontend/framework/`, `pytest11` plugin, etc.), file or apply, resume. **Anti-pattern**: *"not yet — recurrence rule hasn't tripped"* without naming a threshold or logging a trip-counter — that's vague and lets drift accumulate undetected. Audit trail this session — formalizations driven by this rule: vitest config (7 instances → factory), conftest bind-consent-mock (3 → helper), main.py catalog import (6 → `consent_features=` kwarg), conftest test-bootstrap (would-be 6 → `pytest11` plugin), settings-page mounts (would-be 6 → seed-mounted route), spend-badge mounts (would-be 6+1 → `DEFAULT_AI_BADGES`). Companion to `Replication-to-seed symmetry` (language-time trigger), `Active robustness review` (execution-time trigger), and `Audit seed completeness proactively` (retroactive sweep) — together these four form a complete fence around DRY-into-seed at every observation moment. → `KNOWLEDGE-BASE/CONTEXT/PATTERNS/project-execution.md § 2.7 The recurrence rule`
- **Active robustness review during execution — every phase doubles as an inspection pass.** Phase execution is not "ram through §6 sub-tasks." It is *also* a proactive inspection pass on the code you're touching + the surrounding code + the contract it implements. While editing, your eyes are open: silent error swallows (`except: pass`), stale TODOs, untyped `any`/`unknown` that should be narrowed, race conditions in async chains, hardcoded magic numbers, missing validation at trust boundaries, fields populated in one place and never read, mock-vs-real divergence. Capture findings live in the phase's `**Improvements:**` block — one bullet per finding, in-the-act phrasing — NOT saved for "later." Apply low-risk inline in-scope; defer out-of-scope to follow-up projects (scaffold the folder from `templates/PROJECT-TEMPLATE.md` immediately — broken pointers are forbidden). **Anti-pattern**: phase ✅ with `**Improvements:** none identified.` after a non-trivial phase that touched many files — almost always means the inspection pass was skipped. **Counter-anti-pattern**: scope-creep refactors of unrelated code; notice broadly, act narrowly. Typical phase touching 3-10 files: 1-5 improvement bullets. → `KNOWLEDGE-BASE/CONTEXT/PATTERNS/project-execution.md § 2.6 Active robustness review`
- **§6 ↔ §11 consistency self-check before claiming a phase is done.** Recurring slip pattern (caught 2026-04-27, multiple times in one session): writing rich §11 Change-Log entries that say "Phase N ✅ shipped" while §6 still shows `- [ ]` checkboxes and an unflipped header. **Before any reply that claims a phase is closed, verify all five:** (1) §6 header carries `✅`, (2) every §6 sub-task is `- [x]`, (3) `**Improvements:**` block is filled (or `none identified.`), (4) §11 entry exists, (5) `improvements.md` regenerated. **If any of 1-5 is missing, the phase is NOT closed — fix the live state first, then claim done.** The narrative is allowed to be terser than the live state; the live state is NEVER allowed to lag the narrative. Detector formalization filed as `keeper-phase-state-consistency-detector`. → `KNOWLEDGE-BASE/CONTEXT/PATTERNS/project-execution.md § 2 Self-check before claiming a phase is done`
- **Projects live next to the code they touch — three valid locations, scope-scoped.** Projects go in one of exactly three places, driven by scope: `projects/<slug>/` at the repo root for **cross-product, seed/platform-infra, or not-yet-a-product migrations** (`adconnect-migration`, `repo-state-consolidation`, `strict-mode-migration`); `products/<product>/projects/<slug>/` for **single-product scope** (`products/personal-finance/projects/pf-org-scoping-migration`, `products/therapy-platform/projects/therapy-platform-wiring`, `products/erp-imobiliario/projects/vista-crm-wiring`); and `core/projects/<slug>/` for **core-platform-control-plane scope** (auth, SSO, billing, orgs, entitlements). **Every product has a `projects/` folder (even if empty, pinned with `.gitkeep`)**, including core — the folder is part of the scaffolding convention, not something that appears once a project is filed. *Rationale:* an agent working inside a product should discover its own projects without sifting through unrelated cross-product work; root stays reserved for platform-level efforts. Slugs are globally unique — the MCP tool resolves `project="<slug>"` to whichever folder holds it. Each project folder holds `PROJECT.md` (living document) + `improvements.md` (auto-generated) + `proposals/` (per-phase bundled proposals). **Always start a new project by copying `templates/PROJECT-TEMPLATE.md`** into the correct location based on scope; fill placeholders, delete sections that don't apply. Follow the slug naming convention (`<subject>-<intent>`) in `KNOWLEDGE-BASE/CONTEXT/PATTERNS/project-execution.md §8`. **Before drafting or revising a project, act as a questionnaire** — ask clarifying questions, confirm constraints, surface edge cases. Never assume. **Write every project for a zero-context reader** — assume the next agent to pick it up has not seen the conversation that produced it (the drafter may `/clear`, context may auto-compact, another session may inherit the work). Inline context in §1, quote the user in §2, name files with paths in §5, pair every §7 Open Question with an evidence-backed recommendation, and make §10 commands copy-paste ready. Details in `KNOWLEDGE-BASE/CONTEXT/PATTERNS/project-execution.md §10`. **During execution, tick tasks live** (`- [ ]` → `- [x]`, saved immediately — never batched), because the user watches the file as a live dashboard. **Cadence is phase-by-phase by default**: execute one phase, then pause and wait for "continue"/"next phase". The user overrides with throughput instructions like "ram through 1-3" or "do all backend phases". **Phase headers carry a status icon** (no icon = pending, `⏳` = partial, `✅` = complete, `❌` = blocked). Flip to `✅` only when every sub-task inside is ticked. **Improvement flow is capture-then-synthesize**: (capture) during step implementation, drop quick specific bullets into the phase's `**Improvements:**` block — no ceremony, in-the-act notes; (synthesize) at end of phase, BEFORE flipping the header to `✅`, read the entire block, consider the whole project context, and file **ONE bundled proposal per phase** via `noctusai_file_proposal(project="<slug>", ...)` — the proposal lands in the project's own `proposals/` folder (whichever of the three locations the project lives) with `Origin: project:<slug>:phase-<N>` and filled `Context`, `Situation`, `Proposed Solution` (bundled improvements as independently-executable items), `Effects`. Not one proposal per improvement — ONE per phase, bundling them. Each bundled improvement retains individual execution (reviewer schedules separately). Then flip header to `✅`, run `python mcp/noctusai/cli.py --improvements <path-to-PROJECT.md>` to regenerate `improvements.md`. → `KNOWLEDGE-BASE/CONTEXT/01-PHILOSOPHY.md` (Projects are living) + `KNOWLEDGE-BASE/CONTEXT/PATTERNS/project-execution.md §1` (three-location rule) + `KNOWLEDGE-BASE/CONTEXT/PATTERNS/proposals-and-improvements.md` (two-system protocol)
- **Triage at decision time — formalize / refactor / accept-with-rationale.** Divergences from ideals (contract violations, architectural drift, pattern inconsistency) get evaluated at the moment they're surfaced, not upfront. Every surfaced divergence lands on one of three explicit outcomes: **formalize** (extend framework/seed to make the pattern a named seam), **refactor** (bring the offender into compliance with the existing contract), or **accept-with-rationale** (legitimate product/project divergence — document WHY in §11 / MASTER-PROMPT.md). "Accept" is a real landing; the paperwork keeps it from being silent. Recurrence across products flips prior `accept` outcomes toward `formalize`. Counts of formalize/refactor/accept over time are a health signal for the framework's coverage. *The workflow evaluates itself as it goes — no upfront ideological rulings.* → `KNOWLEDGE-BASE/CONTEXT/01-PHILOSOPHY.md § Triage at decision time`
- **No silent errors — always explicit fix opportunities.** Every failure mode surfaces loudly in the user-facing output: no `except: pass`, no silent degraded-mode fallbacks, no deferred items without a named destination, no "verification: ✓" when the tail of the output showed red. When a tool fails, a dependency is unavailable, or an assumption was needed, say so explicitly with the exact error and the proposed fix path. Ambiguity is a silent error — ask. Absence of findings is a claim — quote the command that confirms it. *Loud-and-fixable beats quiet-and-working-most-of-the-time.* Load-bearing implementations: `MockSupabaseClient(validate_schema=True)` default (closes the wrong-column silent-fail class by cross-referencing mock filter/select/insert calls against migration files — `KB § PATTERNS/testing.md § Schema validation`); `check_mock_schema_validation` keeper detector (flags silent opt-outs without rationale). → `KNOWLEDGE-BASE/CONTEXT/01-PHILOSOPHY.md § No silent errors`
- **Clean folder — every artifact has a home, nothing lives loose at repo root.** Repo root holds only platform-wide files (CLAUDE.md, README.md, docker-compose.yml, .gitignore, scripts pointer). Audits, proposal drafts, design notes, scratch `.md` files created by any agent belong inside a project folder (`projects/<slug>/`, `products/<product>/projects/<slug>/`, or `core/projects/<slug>/`) as first-class reference artifacts quoted by PROJECT.md §1/§5. When you find a stray root file: scaffold the project, move the file in as a reference artifact (e.g., `CODEX-AUDIT-REFERENCE.md`), inline the load-bearing bits into PROJECT.md, delete the root copy. Never leave stray files "for later" — they violate the principle and silently mislead the next agent. Prefer ONE umbrella project grouping related findings over N scattered one-finding folders. *Inventory discipline — same logic as apply-inline-then-delete and empty-`proposals/`-folders.* → `KNOWLEDGE-BASE/CONTEXT/PATTERNS/project-execution.md § 11 Clean-folder principle`
- **Apply proposals inline, then delete — every deliverable ends with a short summary.** When a phase-end proposal is filed via `noctusai_file_proposal`, the same session MUST apply every item that can be applied (low-risk, in-scope, self-contained), document deferrals with a live pointer (new project folder scaffolded from `templates/PROJECT-TEMPLATE.md`, backlog entry, next phase sub-task), and **delete the proposal file** so `proposals/` stays clean (`.gitkeep` only). A deferred item referencing a follow-up project MUST create that project folder — prose references to nonexistent projects are broken pointers. Every reply concluding non-trivial work MUST end with a list-shaped summary covering applied items, deferred items (with destinations), and a one-line verification. No silent finishes, no multi-paragraph narratives. *This is the default protocol, not a user override — it applies to every agent on every deliverable.* → `KNOWLEDGE-BASE/CONTEXT/PATTERNS/proposals-and-improvements.md` § 4b + § 4c
- **Finish the session — verify, don't assume.** Before closing a working session (or ending a multi-turn task), run the end-of-session checklist: (1) `cd products/erp-imobiliario/frontend && npx vite build`, same for `products/core/frontend`, `products/therapy-platform/frontend`, any touched product frontend; (2) `cd products/<touched>/backend && pytest` for every backend that got code changes; (3) `cd mcp/noctusai && pytest tests/` for MCP-toolkit changes; (4) report any regression — don't mark work "done" while a build or test is red. *Every in-session change must land on green.* The checklist lives at the top of `projects/<slug>/PROJECT.md → §10 How to use this project` when a project has non-obvious verification steps; otherwise the four commands above are the default.
- **Gamification is subtle.** Rankings, points, progress bars — always discrete; always with a ⓘ info icon explaining the formula; always tied to real business activity (never "logged in today"-style rewards). → `KNOWLEDGE-BASE/CONTEXT/07-GAMIFICATION.md`
- **Three-way sync — KB, CLAUDE.md, and memory move together.** Any rule, methodology, or behavioral change lives in **all three layers simultaneously**: (1) the topical KB file + `INDEX.md`, (2) CLAUDE.md (the pointer layer, loaded every turn), (3) the memory file under `~/.claude/projects/.../memory/` + the `MEMORY.md` index. Updating one without updating the others creates drift the next agent can't see. **Triggering events that mandate three-way sync:** (a) any `feedback_*.md` memory file added/modified → corresponding KB section + CLAUDE.md pointer must exist; (b) any KB rule change → memory entry filed (if user-preference-shaped) + CLAUDE.md pointer updated; (c) any CLAUDE.md rule change → KB depth + memory must back it. **Ordering when introducing a NEW rule:** KB-first (topical file + INDEX.md), then CLAUDE.md pointer, then memory entry citing both. Never the reverse — CLAUDE.md is the pointer layer and stranded pointers (pointing into nonexistent KB content) violate the rule. **Ordering when amending an existing rule** (e.g. extending it, adding caught-instances): all three layers in the same session — partial updates lie about the rule's current state. Tiny typo-only fixes (single layer) are exempt. The `verify-kb-sync.sh` pre-commit hook catches dangling KB↔CLAUDE.md pointers but cannot catch missing memory entries — that discipline is the agent's. Also: `mcp/noctusai/README.md` updates if tooling changed. → `KNOWLEDGE-BASE/CONTEXT/01-PHILOSOPHY.md § Docs stay in sync`
- **MCP migrations mirror the file.** When you apply DDL via the Supabase MCP (`apply_migration` or `execute_sql`), the same SQL **must** exist as a numbered migration file in `products/<name>/backend/migrations/NNN_<name>.sql` — commit both together. *The database is mutable state; the migration files are the authoritative replay log.* If the file drifts from what was applied, a fresh clone cannot reproduce the schema. Write the file first, then apply via MCP (or if you iterated live, back-port every change into a new file before committing). → `KNOWLEDGE-BASE/CONTEXT/PATTERNS/database-rls.md`
- **Supabase MCP is the agent's tool — use it proactively.** When a task needs DB access (apply a migration, audit a schema, verify RLS, seed or inspect data), the agent executes it directly through `mcp__claude_ai_Supabase__*`. **Never** ask the user to paste SQL into the Supabase editor or grant one-off permission — blanket approval stands for this repo. Still use `apply_migration` for DDL (per the rule above); `execute_sql` is for read-only inspection only.
- **`CLAUDE.md` vs `KNOWLEDGE-BASE/` — the token budget rule.** This file is loaded every turn; keep it lean. The KB is loaded on-demand; put depth there. *The split exists to save tokens each iteration without losing knowledge — if CLAUDE.md grows, context degrades.*
- **Every product has `README.md` + `MASTER-PROMPT.md`.** README for humans browsing the repo; MASTER-PROMPT for agents building features. Both are mandatory from day one of a new product. → `KNOWLEDGE-BASE/CONTEXT/GUIDES/new-product.md`
- **LGPD-first, always.** Whenever code touches personal data (identity, financial, clinical, behavioral, derived embeddings, …), the LGPD lens is the first lens — before functionality, before performance, before UX. Clinical text is Art. 11 sensitive data; it never leaves the Therapy schema without a documented basis, never hits a response cache. When in doubt about an approach, call `noctusai_lgpd_flag(...)` — it records the concern in `LGPD-WARNINGS.md` and notifies the user; **it does not block.** The flag is a checklist item: it gets ticked when the concern is resolved. → `KNOWLEDGE-BASE/CONTEXT/PATTERNS/lgpd.md`

## 4 · Sync rule

This file and `KNOWLEDGE-BASE/INDEX.md` must stay in sync — when you add, rename, or delete any KB file or folder, both get updated.

**Pre-commit hook enforces it automatically** (`scripts/pre-commit` → installed by `scripts/install-hooks.sh`). On every commit the hook:

1. Syncs `products/seed/` → `templates/product-seed/` if staged.
2. Runs `scripts/update-kb-counts.py` — regenerates auto-derived count blocks (product inventory, schema tables, MCP tools) and stages any updated docs.
3. Runs `scripts/verify-kb-sync.sh` — **blocks the commit** if any pointer in this file doesn't resolve, or if any KB doc is missing from `INDEX.md`.

Manual runs (for debugging or CI):
- `bash scripts/verify-kb-sync.sh`
- `python scripts/update-kb-counts.py [--check]`
- `python mcp/noctusai/cli.py --verify-kb-sync`

To install hooks in a fresh clone: `bash scripts/install-hooks.sh` (or the full setup: `bash scripts/setup.sh`).

Bypass the hook (rarely correct): `git commit --no-verify`.
