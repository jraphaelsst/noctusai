# Roadmap — orbity-noc: build → dev deploy (2026-06)

> **Goal.** Stand up **orbity** as a navigable noc product **deployed on the dev fleet**, so the user can navigate the platform, run its tests, and **validate the dataflow + backend integrations** before promoting to prod as `orbity.noctusai.com`. Built via the **seed-first capability-uplift loop** (`KB § GUIDES/absorb-seed-workspace.md` learning-absorption refinement): orbity consumes seed organs; it does not fork. `erp-imobiliario` is the near-isomorphic cousin/pilot for the Tier-1 organs.
>
> **Source knowledge:** `KB § ABSORPTIONS/orbity/` (faithful diagnostics, neutral comparison, salvage eval, seed-first strategy). **Tracked in** `project-history/absorptions.ndjson` (`noctus.dev.absorption_status`).

## Guiding decisions

- **Consume, don't fork.** Wherever erp-imobiliario / social-wiring / core / seed already ship an organ (CRM funil, contratos, agenda, whatsapp, meta, notifications, recorrencia, portal), orbity consumes it via `@noctusai/lib/...` / module registration. Net-new organs (finance DRE+closure, Meta CAPI, automation engine, Asaas/Conexa) are built seed-first, pilot on erp, then orbity consumes them — **orbity is the last consumer**.
- **Tenancy:** orbity's `agency` = noc `org` (`core.organizations` + `current_org_id()` RLS). No agency-specific tenancy fork (the diagnostic confirmed Orbity's RLS is already org-shaped).
- **Absorb the intent, not the code.** Re-implement on noc's disciplined seam (RLS-via-trusted-table, encrypted creds, no silent fallbacks, contract-first) — NOT Orbity's weaknesses (open finance RLS, plaintext tokens, mock-data fallbacks). See `KB § ABSORPTIONS/orbity/13-SALVAGE-EVALUATION-BAD-CODE.md`.
- **Deploy incrementally.** The FIRST evaluable dev milestone = navigable core + key backend integrations (P0–P2). Deep finance/automation (P3–P4) deepen after the user's first eval. "Deployed on dev" is reached at P5 (container + start.sh + smoke) and re-run each phase.
- **Parallelize.** File-disjoint module slices dispatched to backend/frontend engineers in waves; tech-lead integrates + gates. Contract-first (author FE↔BE + DB/RLS contracts before dispatch).

Live evaluation finally performed 2026-07-20.
- **M2: + P3 (financeiro)** — DRE + closure live; erp pilot also gains it. → ⬜ **not started.** Financeiro today is CRUD-only: contracts/expenses/revenues + a cash-flow hub. No DRE, no month-end closure, no dunning.
- **M3: + P4 (automation + CAPI + BR-fiscal)** — full agency operating model. → ⬜ **not started.** Automação has a real state machine but no scheduler and a Fake sender; Meta CAPI and Asaas/Conexa unbuilt.
- **M4: prod promote** — `orbity.noctusai.com` (dev-validated build, explicit consent). → ⚠️ **reached ungated on 2026-06-03; consent given retroactively 2026-07-20.**

## ⚠️ Incident — prod exposure without consent (2026-06-03 → resolved 2026-07-20)

Orbity became a production-serving product **the same day it was scaffolded**, six weeks before any validation, while every phase above was still ⬜.

**Causal link:** commit `679d0838` "onboard orbity to the prod fleet" registered the slug on the three prod-exposure surfaces — `deploy/fleet/docker-compose.prod.yml`, `deploy/tunnel/ingress.yml`, and `ALL_SLUGS` in `scripts/infra/build-and-push.sh`. **Editing those three surfaces IS the promotion decision.** Everything downstream (bless → main-push CI build → `:latest` → fleet pull) is faithful automation of a declaration already made. Nobody deployed orbity; it simply became true.

**Scope (checked before claiming severity):** systemic-*by-absence*, not by repeated violation. The other nine products entered prod via `18dce993`, a reconciliation importing already-live VPS state into git — they predate the tooling. Orbity is the first product to walk the prod-onboarding path since the tooling existed, and it walked it ungated. There are no other offenders to audit for.

**Closed by:** keeper `check_prod_exposure_consent` (`db72c18c`, 2026-07-20) — fires once per product on first prod-surface arrival, requires a user-authored `deploy/consent/<slug>.prod.yml` committed in isolation, and is silent forever after. Verified live in both directions (fires on a new arrival; silent on routine commits). Depth: `KB § PATTERNS/devops/prod-exposure-consent.md`.

**Not covered by that gate:** the rollout half — the fleet runs floating `:latest` rebuilt from `main`, so `release stage=promote` pins a branch that governs nothing that runs. Tracked separately.

## Decision log

- 2026-06-03 · Roadmap opened. Build via seed-first uplift; erp-imobiliario = pilot cousin. Incremental dev deploy; M1 = navigable core + backend integrations.
- 2026-07-20 · **Live browser evaluation against prod.** Confirmed working: SSO, Clientes (real CRUD), Tarefas, Agenda, CRM engine. Confirmed broken/absent: funnel empty for every org, Dashboard+Landing still seed boilerplate, Example module still registered, malformed public tokens 502-ing, Meta "connect" a phantom manual form.
- 2026-07-20 · **Meta connect — seed-lift, not consume.** The seed ships the hard half real (`noctusai_lib.integrations.meta`: Protocol + Fake + real `MetaOAuthAdapter`, full ads surface on real Graph calls, correctly App-Review-gated). It does NOT ship the connect half: `make_oauth_provider` supports `"google"` only, and the working Meta authorize/callback lives solely as product-local code in social-wiring. Orbity is the **N=2 consumer** ⇒ formalize into `noctusai_lib`, never fork social-wiring's router. Interim: Tráfego made honest about having no live sync. **Also blocked on config** — prod has no `META_APP_ID`/`META_APP_SECRET`/`META_SYSTEM_USER_TOKEN` at all, so wiring alone would not function.
- 2026-07-20 · **Funnel seeding mechanism.** Rejected lazy-seed-on-read (a GET silently writing is a surprising side effect) in favour of a migration backfill for licensed orgs + an explicit org-scoped `POST /api/crm/stages/seed-defaults` through the user-scoped client, so RLS is the enforcing layer (no service-role escalation, no cross-org write path). Idempotent app-side and DB-side.
- 2026-07-20 · **Prod-exposure consent gate shipped** (see incident above). Retroactive consent given by the user for orbity.

## Risks / watch

- **Scope:** full agency CRM is large; phase honestly, deploy incrementally, surface depth-vs-breadth tradeoffs at each milestone.
- **Tenancy reconciliation:** agency→org rename must be clean (RLS-via-trusted-table); run `get_advisors type=security` after RLS.
- **Don't inherit Orbity weaknesses** (13-SALVAGE): encrypted creds (no plaintext tokens), no mock-data fallbacks, RLS-via-trusted-table (not USING(true)), single automation impl (not TS+PLpgSQL).
- **dev↔prod parity:** validate in prod-shape (RLS on, real JWT) before M4.
