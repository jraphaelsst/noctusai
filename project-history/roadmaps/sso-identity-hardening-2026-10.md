## Origin

During the SW deal-876 walkthrough the owner logged out of core as `jraphaelsst@noctusai.com` and in as `joao@one.com`. social.noctusai.com kept A's Supabase session in its own-origin localStorage — through a reload and through re-opening SW from the core card — so SW acted as A and audit rows recorded the wrong actor. Root causes (security advisor: HIGH): `SSOCallback` kept any valid local session and threw the core token away unredeemed; core logout revoked nothing (`/api/auth/logout` signed out a fresh anon client); the seed BE auth dependency let a stale `nai_session` cookie win over the bearer; framework products never sent `product_slug`, so core's audience check was skipped.

## Anti-goals (explicit non-goals)

- ❌ "Ask core for its current identity from the product." Core's session lives in core's own-origin localStorage; a product can't read it — convergence is via token redeem + server-side revoke.
- ❌ "BroadcastChannel for cross-product logout." Same-origin only; useless across product subdomains.
- ❌ "Sign out on any `getUser()` error." Only auth rejections; an auth-server outage must never log out the fleet.
- ❌ "Per-browser precise revoke" for core logout — the owner chose global (2026-10-09); revisit only if users complain about other devices.

- **2026-10-10 (P2.2 browser-bind, observe mode)**: Design. Launch (`POST /token`, `GET /launch/{slug}`) mints a fresh `nonce` (token_urlsafe 32) per launch, puts `bnd = sha256(nonce)` in the token and sets cookie `sso_bnd_<jti>` = nonce: HttpOnly, Secure, SameSite=Strict, `Path=/api/sso/session`, Max-Age = token TTL (5 min). **One cookie per launch, named by jti** (not a stable per-browser cookie, not one shared name): a shared/stable cookie overwritten per launch would break a concurrent second launch (two tabs, two products); per-jti names cannot collide, cost nothing (path-scoped to the redeem endpoint, expire in 5 min), and the redeemer finds its cookie from the token's own jti. Redeem sends `credentials:'include'`; core is a single same-origin container whose FE/API share a host, so the cookie lands on core's host and products (sibling subdomains = same SITE) send it on their credentialed cross-origin XHR despite SameSite=Strict; CORS already uses `allow_credentials=True` with the explicit registry origin list (`@registry:all`, no wildcard). Enforcement: cookie present ∧ hash != `bnd` ⇒ 401 `sso_bind_mismatch` BEFORE `_claim_sso_jti` (a relayed token never burns the legitimate one); cookie absent ⇒ allowed, logged `sso_unbound_redeem jti product regime origin` (never token/nonce) because legacy callbacks (orbity, p-studio) and not-yet-rebuilt strict products send no credentials. Absent-⇒-reject sits behind ONE predicate, `unbound_redeem_allowed(regime)` (currently `True`), marked `NOC-REMEDIATE[sso-unbound-redeem-allow]`; flip rule = T6. A matched redeem clears its cookie. Tokens with no `bnd` (minted pre-deploy, ≤5 min) skip the check. Logout does NOT need to clear anything: cookies are single-use, path-scoped, die in 5 min and carry no session. Nonce appears only in Set-Cookie (never URL/body/log). **Residual until T6**: login-CSRF still works against any callback that omits the cookie. Seed touched: `create_sso_token` factory gained optional `jti`/`binding`; `SSOCallback` redeem fetch `credentials:'include'`. Unverified: real-browser behaviour (Strict cookie on the cross-origin XHR) — verify recipe below.
