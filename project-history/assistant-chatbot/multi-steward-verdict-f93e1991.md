# Council f93e1991 — multi-steward topology (full view, seats revealed)

Recommendation: RECOMMENDATION (council informs; stewards decide): shape C + slim E. (a) one serialized merge queue, enqueue/landed open to any session/integration-branch owner without lease; (b) prod (bless/promote/prod migrations/deploy_image) exclusive via a short-held shared action lock, eventually held by the session where the owner typed consent; (c) integration-branch owners deliver small entries tied by atomic delivery groups, not large trains. Defer per-product lanes/leases until telemetry shows queue wait dominates.

Biggest risk: Loosening the lease before a shared prod action lock exists: two sessions/machines could bless/migrate/deploy the one VPS concurrently (lease is local to one Mac, unattributed callers pass). Secondary: atomic groups coarsen ejection.

First step: Fix lease liveness in release_steward.py (boot-id + pid + heartbeat; unknown pid not alive; stale-claim shows last in-flight step), with test + telemetry.

Full chair report incl. build list: see multi-steward-decision.md

## Objections

- **A** (lens:executor, minor) Per-product lanes / per-product leases (shapes D, F) are the most expensive to build on the 8 GB Mac with a per-product migration gate and seed/lib changes hitting every suite: path-scoped suites need a seed/lib-touches-everything escape hatch that makes most batches global anyway, and prod is one VPS with serial deploys. No incident in the brief is a lane-throughput problem (all 11 are ownership/identity/derived-state). Recommend deferring D/F until a measured queue-wait metric exists; ship telemetry (queue wait per entry, lease idle time) first per gate-methodology-sync.
  → accepted: see chair report (multi-steward-verdict-f93e1991.md)
- **B** (lens:contrarian, major) Shapes B and C protect the wrong layer: no deploy tool holds a resource lock (grep for flock/mutex in deploy_image.py, deploy_pull.py, migrate_product.py, release.py finds nothing), and the lease is a per-Mac file ~/.noctus/release-steward.json (release_steward.py:~175-215) that lets session-less callers through as 'unattributed' (release_steward.py:789-798). So 'one releaser' is advisory against a second machine, CI or raw ssh. The dismissed alternative is a short-held action mutex at the VPS/tool (deploy and migrate take it, migration-before-image ordering enforced inside it), so ANY session may ship and the steward stops being a person; that removes failures 2, 3, 4 and 11 instead of managing them.
  → accepted: no lock in deploy/migrate/release tools; unattributed pass-through release_steward.py:787-799; build item 11 owner-gated
- **C** (lens:executor, major) Lease staleness is the only recovery path: TTL 7200 s with claude_pid liveness as the sole fast path (release-steward.md:81-83), yet failure 2 left nobody owning the queue after a reboot until the owner reassigned by hand. Nothing specifies what state a dead holder leaves mid-sequence (migration applied, image not swapped; spec 10 at :72-75). Cheapest increment: on claim over a stale lease, print the last in-flight step from release-steward.ndjson (migration applied? image pinned?) before proceeding.
  → accepted: see chair report (multi-steward-verdict-f93e1991.md)

  → accepted: see chair report (multi-steward-verdict-f93e1991.md)
