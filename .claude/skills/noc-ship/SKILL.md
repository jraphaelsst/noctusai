# noc-ship — release · bless · promote · deploy

`main` = the blessed/shippable release line; production is the further `main → prod` promote the VPS tracks. NEVER push/merge to `main`/`prod` without explicit per-action consent. `dev` = integration branch (push your own work freely).

## Workflow

0. **🔴 PROD-ONLY — the dev FLEET is DORMANT (2026-08-11, owner's decision).** There is no `./start.sh` step and no dev-container smoke; **do not re-add one**. Prod is now first-contact for the running image, so the gate MOVED and TIGHTENED — all three are MANDATORY before bless: (a) `noctus.dev.predeploy_check <slug>` for **every active product** — host-side, runs a REAL `vite build` + the backend suite + prod-config value parity, and is now the primary functional evidence. Three outcomes, not two: `ready` (pass) | `blocked` (a real failure) | `inconclusive` (the harness could not MEASURE — pytest died at collection because the interpreter lacks a dep the product declares). An `inconclusive` is NOT a pass and NOT a product verdict: re-measure with an interpreter that has the product deps, then re-run. A fresh worktree carries no `venv/` of its own, which is how this shape burned two sessions on 2026-09-22 — each re-ran the suite by hand to find the product green; (b) **CI GREEN somewhere in main..dev** — no longer advisory, because a dev-fleet smoke can no longer stand in for it, and **since 2026-08-22 no longer yours to remember**: `release stage='bless'` walks `main..dev` for a QUALIFYING green (2026-09-24, R1 — not necessarily the exact tip) and REFUSES outright only when NOTHING in range qualifies (sole exception, applied automatically: a diff that touches nothing executable — docs + `project-history/` only). It was advisory-in-practice until 2026-08-22, which is how `1c83232f` reached prod red; (c) `--check-prod-exposure-consent` clean. The 🔴 `dev` **BRANCH is UNAFFECTED** — worktree off `origin/dev` → integrate → bless is unchanged; only the CONTAINERS are dormant. Still FF the PRIMARY checkout to `origin/dev` after integrating so hooks + tooling read the shipped tree. → `KB § PATTERNS/devops/dev-fleet-dormant.md`.
1. **Status first** — `noctus.dev.release stage=status` (read-only chain view: dev → main → prod).
1a. **Manifest — whose work rides along (informational).** `noctus.dev.release stage=manifest` (read-only): every commit `main..dev` grouped `Noc-Branch` trailer → branch-tree `project` → ship-consent state. Tell the owner what the release carries.
1b. **Permission = the owner's request (owner decision 2026-09-24).** "No approval needed when I ask — the ask is the permission itself." When the owner asks you to ship/deploy, ship; NEVER ask for a per-project approval phrase. The one gate kept: a NEW product's first prod exposure (`prod_consent`, see the prod-exposure precheck below).
2. **Bless — no freezing on a bookkeeping tail (2026-09-24, R1).** `noctus.dev.release stage=bless` (default `mode=ff`) FFs `main` → the NEWEST commit `main..dev` that carries a QUALIFYING green `Tests & Build` run — not necessarily the exact dev tip. A "qualifying" green is one whose heavy jobs demonstrably ran (never a run that merely skipped everything and read "success"); result surfaces `blessed_sha` + `skipped_tail` (the newer, not-yet-verified commits left on dev — normal steady state for a rapid branch-pointer/salvage/ledger train, never something to chase; `skipped_tail.migrations` names any migration files IN that unverified tail — R4). Never wait on CI or ask peers to hold dev pushes before blessing anymore: a red or pending TIP no longer blocks a bless of an already-verified ancestor. A diverged `main` is refused until `stage=backmerge confirm=true`; bless refuses outright only when NO commit in range has a qualifying green (docs-only diffs keep their CI exception). If you genuinely need the very tip verified (e.g. it's the only thing that changed), dispatch a full run: `gh workflow run test.yml --ref dev` — never auto-run this yourself, only suggest it. Opt-in `mode=cut` ships only approved work (see the KB pattern); `mode=refuse` blocks on unapproved work. DRY-RUN by default; it is the ONLY sanctioned setter of `NOCTUS_ALLOW_MAIN_PUSH`. → `KB § PATTERNS/devops/ship-consent-riders.md` · `KB § PATTERNS/devops/dev-main-ci-gates.md`.
3. **Promote** — `noctus.dev.release stage=promote` snapshots `prod` → `prod-backup` (rollback pointer) then FFs `prod` → a blessed `main` sha. `confirm=true` to push.
3a. **Backmerge after a cut** — `noctus.dev.release stage=backmerge confirm=true` merges `main` into `dev` (merge commit, no checkout) so dev contains main again and the next bless can FF.
4. **Deliver to VPS** — code: `noctus.dev.deploy_pull` (§2a safe pull: inspect → ff-only → verify; never reset/checkout/clean on the VPS). Image model: `noctus.dev.deploy_image` (atomic GHCR pull + health-probe + auto-rollback + SWAP-VERIFY: after a healthy probe it re-inspects the RUNNING container's own image id + revision label and refuses `status='deployed'` — reports `swap_unverified` instead, no auto-rollback — unless the swap verifiably landed; 2026-08-13, a healthy OLD container had silently never been recreated). **Migrations — apply EXACTLY what got blessed (2026-09-24, R3).** `noctus.dev.migrate_product sha=<blessed_sha>` reads migration files via `git show <blessed_sha>:<path>`, never the working tree — a bare `migrate_product` (no `sha=`) against the working tree would also pick up any unverified migration still sitting in bless's `skipped_tail.migrations`. Always pass the `blessed_sha` bless just returned. If you've lost it: the last-blessed sha is `origin/main`'s current tip (bless FF-pushed exactly that sha) — `git rev-parse origin/main`, NOT `noctus.dev.release stage=status`'s `qualifying_target` (N4, compliance review, 2026-09-24). `stage=status`'s qualifying-target field is the candidate for the NEXT bless (forward-looking), not a record of what a PAST bless already shipped — reading it here would silently re-migrate to whatever main..dev now qualifies as, which can be newer than what's actually on prod's `main`.
5. **Pre-deploy gate** — `noctus.dev.predeploy_check` (D3 manifest + prod-config parity: catches present-but-localhost values the boot guard can't).
6. **🔴 Post-deploy PROD verification — MANDATORY, two legs, same weight, was optional.** With the dev fleet dormant this is the ONLY runtime evidence the platform gets, so a deploy is not "done" until BOTH pass:
   - **(a) REVISION-DRIFT — `noctus.dev.deploy_verify`** (or `--deploy-verify`). The INDEPENDENT witness: it has zero dependency on `deploy_image` having run, succeeded, or even existed in this process. Roster is CATALOG-DRIVEN (`ativo=true AND deploy_scope='live'` + `core`) — **not** raw-sha-inequality over the compose fleet: a `ativo=false` product can never reach the prod tip, so flagging it would go red forever and train people to ignore the gate; a catalog-live product with NO container at all now surfaces as its own `missing` finding (a compose-driven loop could never see that). The drift predicate itself is build-scope-aware, not literal: running an older revision is the NORMAL steady state (images rebuild only when their build scope changes) — `deploy_verify` diffs the running revision against the prod tip and reuses `deploy_pull`'s build-scope oracle to ask whether that diff actually touches the product's own inputs (or any fleet-wide `seed/`/Dockerfile/compose path); only THAT is `drift`. `status='verified'` (exit 0) is the only pass. **If `deploy_image` times out, or the MCP session disconnects mid-call, that is NOT success by default** — treat it as `status=unverified` and run `deploy_verify` immediately to get ground truth; never assume the swap landed because the call went quiet (2026-08-13: exactly this — `deploy_image` timed out, the MCP server disconnected before reporting anything, and only a manual `docker inspect` caught prod still serving the old image).
   - **(b) HEALTH/CONTENT** — `noctus.vps.health` all-healthy, then each ACTIVE product's `/api/health` answering 200 both internally (`noctus.vps.exec --container`) and through the public edge (browser UA — CF WAF 1010). Read `startup_hook_error` in that payload too: a product whose lifespan hook failed still serves 200 and reports it there, so `status: "ok"` alone is not the answer (`KB § PATTERNS/backend/startup-hook-must-not-be-fatal.md`).

   On a `deploy_verify` drift OR a health failure, ROLL BACK (`deploy_image` auto-rolls a failed health probe; code rolls back to `prod-backup`) — do not debug forward in prod.

6a. **🔴 Then `noctus.dev.spa_smoke` — the FRONTEND leg (step 6 is backend-only).** Every check in step 6 passes while the JS bundle is missing: the container is up, `/api/health` answers, and the edge returns 200 for the HTML **shell** — a blank page for every user, all gates green. `spa_smoke` asserts, per active product, that the shell carries a mount point + bundle tag, that the bundle is real JS (**not** the SPA HTML fallback, which also 200s), and that a deep link resolves (client routing wired). After a UI-library change, pin what shipped with markers: `expect_absent=["@remix-run/router"]` proves a react-router v7 bundle. It does NOT execute JS, so an in-component render crash is still uncovered — that limit is deliberate. → `KB § PATTERNS/devops/prod-deploy-safety-gates.md`.

## Guardrails
- R4 human-gated: PRESENT {push cmd + range + evidence} → explicit user go → execute. Never auto-push `main`/`prod`.
- **No more manual `/mcp` reconnect for a stale toolkit (2026-09-24).** `release`/`migrate_product`/`deploy_image`/`task_branch`'s confirm=True writes no longer hard-refuse when the MCP server's module graph is stale — they transparently re-run in a fresh `python mcp/noctusai/cli.py` subprocess against the current on-disk code (result carries `executed_via="fresh_subprocess"`); a restart is still the right long-term fix, just no longer a blocking prerequisite for the write in front of you. The fresh child gets up to 1800s (F2/N-round, 2026-09-24) before ITS OWN timeout fires — long enough to cover a real deploy/migration, but also longer than most MCP-client call timeouts: **if your MCP client times out first, that is NOT the same as the child failing** — the child may still be running or may have already finished. Treat a client-side timeout as `status='fresh_subprocess_outcome_unknown'` yourself and go verify: each tool's result (when it DOES come back) carries a `verification_step` naming the read-only check to run (`deploy_verify` / `migrate_product` dry-run / `release stage=status`) — that is the ground truth, never a re-guess from the client-side timeout alone. → `noctus.dev.toolkit_freshness`.
- 🔴 **The dev FLEET is dormant — prod-only (2026-08-11).** Never `./start.sh` as part of shipping, never re-add a dev-container gate, never "restore" the fleet as a side effect. The `dev` BRANCH is untouched. Raising the fleet again is the owner's cost decision. → `KB § PATTERNS/devops/dev-fleet-dormant.md`.
- The slim prod image is structurally different (no start.sh/registry/node, baked dist, env-only config) — and it is now the FIRST shape any change runs in, which is exactly why `deploy_image`'s health-probe + auto-rollback is the load-bearing net (`noc` highest-recurrence drift class).
- Prod services sit behind the CF tunnel ⇒ any programmatic caller needs a browser User-Agent (1010 WAF). SSO verify: `noctus.dev.sso_smoke`.
- **Prod-exposure precheck** — before promote, `python mcp/noctusai/cli.py --check-prod-exposure-consent` (should already be clean; the pre-commit gate refuses an un-consented product registration at commit time). Bless/promote ships to the newest CI-qualifying-green commit when the owner asks (step 1b) — it is NEVER a per-product "should this be public" decision. An agent may RECORD the user's decision but never invent one: ask them to type the canonical phrase (`prod_consent action=challenge slug=<slug>`), then `action=author`, which REFUSES unless that phrase is verified against the session transcript. → `KB § PATTERNS/devops/prod-exposure-consent.md`.
