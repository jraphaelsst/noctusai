# noc-self-branch — isolate every write off `dev`

🔴 **Absolute rule (user mandate):** NO agent works directly on the `dev` checkout. The FIRST action on any change-producing task is to self-branch. `dev` is a clean idle integration anchor, touched ONLY as a ref at integrate. Reads/chat stay on `dev`.

## Workflow

0. **Residue sweep (drift-fix-on-contact §0).** BEFORE `task_branch action=start`, scan for the recurring git-leftovers drift class (untracked at repo root, worktree-uncommitted state on peer trees). One call: `git status --porcelain` at the primary + glance at `git worktree list --porcelain`. Drift found ⇒ apply the on-contact drill (PAUSE → resolve → surface-if-blocked → update docs → continue) BEFORE forking the new worktree. The clean tree is the precondition for clean parallel work — leftovers absorbed into your fresh worktree become your problem. → `KB § PATTERNS/common/drift-fix-on-contact.md`
1. **Start** — `noctus.dev.task_branch action=start slug=<kebab-task>` (dry-run → `confirm=true`). Forks `.claude/worktrees/<slug>` on `feat/<slug>` off `origin/dev`. `wire_env` DEFAULTS TO TRUE (2026-09-17) — the worktree comes ready to run FE gates (vite build / vitest) by construction; pass `wire_env=false` only to skip the symlink pass on a doc-only slice. The product `node_modules` overlay is SCOPED to the products your `paths` name (`products/<slug>/…`) — pass `paths` for any FE slice, or `wire_products=[slugs]` / `['*']` to override (2026-10-09).
1b. **Publish your branch-pointer right AFTER start, BEFORE the first edit** — `noctus.dev.branch_pointer action=append branch=feat/<slug> base=origin/dev commit=<HEAD> role=engineer agent=<slug> parent=<self|tech-lead> paths=[…] status=on_going brief="…" push_dev=True`. This publishes your collision zone to the global live map before you touch a file (depth: `KB § PATTERNS/architect/branch-tree-tracking.md`). NEVER skip — a missing pointer mis-routes a peer's collision decision.
2. **Work + commit IN the worktree** — every Edit/Write/commit happens under `.claude/worktrees/<slug>/`. **Address files by ABSOLUTE worktree path, not by `cd` + relative path**: the harness runs each tool call with its own working directory, so a `cd <primary>` inside one Bash call silently re-points the next relative write at the primary tree — that is the exact shape of both 2026-08-18 slips. `pwd` confirms nothing about the NEXT call. **On EVERY commit (+ mid-flight when it fits)** → `noctus.dev.branch_pointer action=update branch=feat/<slug> commit=<new-HEAD> notes="<commit msg>"` (push_dev defaults True). Pointer pushes are lag-free (the ndjson is excluded from the cache-refresh hooks).
3. **Enqueue — the ONE path into `dev` (2026-11-05).** Check locally first, scoped to what you touched: your product suite, plus the repo-wide toolkit gates if you touched `mcp/`, migrations, KB or compliance surfaces (`noctus.dev.gate_sweep` derives the set). Then run `noctus.dev.task_branch action=enqueue slug=<slug> confirm=true`. It rebases onto `origin/dev`, renumbers colliding migrations, runs the doc-staleness and pre-push keepers, and pushes to `mq/<slug>--<sha7>`. It does NOT run the merged-tip gates on this machine. GitHub runners test your slice on top of `dev` plus the queue ahead of it, then land it (green), bisect a red batch, or eject it with the reason. NEVER push code to `dev` directly. → `KB § PATTERNS/devops/merge-queue.md`
4. **Landed → cleanup.** Check with `task_branch action=landed slug=<slug>`: it reports queued / pending / ejected / landed. Once it says landed, run it again with `confirm=true`: pointer → integrated, primary FF, worktree + merged branch torn down (skipped if the tree is dirty; `keep_worktree=true` opts out). Your cwd is GONE afterwards: `cd` to the primary. Ejected ⇒ read the reason (it links the CI run), fix it on the branch, enqueue again. Fallback, only when GitHub Actions itself is down: `task_branch action=integrate confirm=true` (local gates + direct FF push; say so in your report). Crashed or by hand ⇒ `task_branch action=cleanup slug=<slug> confirm=true`; the SessionStart sweep reclaims merged+clean+idle worktrees anyway.

## Guardrails

- **Cross-tree hazard:** `noctus.dev.*` MCP tools run from the PRIMARY CWD. Prefer the CLI from inside your worktree (`<primary>/mcp/noctusai/.venv/bin/python <primary>/mcp/noctusai/cli.py --task-branch enqueue --task-branch-slug <slug> --task-branch-confirm`) whenever a peer is active.
- **Small slices, ~3–4 writers.** One branch = one concern, enqueued as soon as it is green; never a long-lived multi-slice branch. Keep about 3–4 sessions writing code at once — beyond that the queue and conflict odds grow, not throughput. Your branch-pointer `paths` (step 1b) is your claim.
- **REPO_ROOT cross-tree resolution (fixed 2026-05-26, N=3 codified):** `cli.py` / direct python imports invoked from inside a worktree now auto-resolve `REPO_ROOT` to the worktree (via `workspace._detect_worktree_root` — boundary detection on `.claude/worktrees/<slug>/`). Explicit lever for edge cases: `NOCTUSAI_HOME=$PWD python mcp/noctusai/cli.py ...`. Verify the keeper's view matches the worktree before relying on it; if it doesn't, that's a regression on the workspace resolver — surface to the tech-lead.
- **A raw `git worktree add` is venv-less — prefer `task_branch action=start`.** There is no per-worktree python venv either way (a fresh worktree always runs `.py` gates via the PRIMARY's `venv`/`mcp/noctusai/.venv`, never a worktree-local copy — those are the "venv" part of the caveat, unaffected by `task_branch`); what `task_branch action=start` DOES now provision, by default (`wire_env`, 2026-09-17), is the `node_modules`/`@noctusai` symlinks a bare `git worktree add -b feat/<slug> <path> origin/dev` never creates. Either way, a bare `python mcp/noctusai/cli.py …` inside a fresh worktree hits the venv-less self-exec → `ModuleNotFoundError: No module named 'noctusai_lib'` unless you pass `--worktree-path`. If you used a RAW worktree (bypassing `task_branch`), wire the node env by hand (§5a) or re-run `task_branch action=start` for the same slug, and run gates via the MAIN repo venv exactly as the pre-commit hook does: `<primary>/venv/bin/python <wt>/mcp/noctusai/cli.py --<flag> --worktree-path <wt>` (MCP-toolkit gates: `<primary>/mcp/noctusai/.venv/bin/python -m pytest tests/` with cwd = `<wt>/mcp/noctusai`, OR the PRIMARY's plain `venv/bin/python -m pytest <wt>/mcp/noctusai/tests/`). Never bare `python cli.py` in a raw worktree. → `KB § PATTERNS/common/self-branching-mode.md §5a`.
- **The gate now refuses the write, not just the commit.** A `PreToolUse` hook (`.claude/settings.json` → `scripts/hooks/claude-guard-primary-write.py`) denies any Edit/Write/Bash write whose target resolves into the PRIMARY checkout while it sits on `dev`/`main`/`prod` — `cd`-then-write included, since it parses the `cd` out of the command. Reads are never blocked, and the orchestrator's own `git pull`/`merge`/`push`/`worktree` in the primary stay exempt by name. If you see that refusal you are in the wrong tree: branch, don't work around it (`NOCTUS_ALLOW_PRIMARY_WRITE=1` exists and is almost never the right answer). → `KB § PATTERNS/common/self-branching-mode.md §11`.
- Never `git switch`/`reset` the shared `HEAD` under a peer (the §9a 2-day-chaos sin).
- "Inline" (no dispatch) ≠ work-on-`dev` — you still branch. The inline cutoff is size-only and orthogonal.
- A worktree is **invisible to the running env** — unit-green there ≠ live works. Integrate + live-probe before calling a UI feature done.
